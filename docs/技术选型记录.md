## 关键决策记录

### 决策 1：为什么用 Bun 而不是 Node.js

- **背景**：项目组大部分成员是零基础学生，需要尽可能降低环境配置复杂度
- **选项**：Bun vs Node.js 20 + pnpm
- **决策**：Bun (1.3.11)
- **理由**：
  - 一体化（包管理 + 运行时 + 测试），一条命令装完
  - 原生支持 TypeScript，不需要 ts-node 或编译步骤
  - 比 Node.js 快，monorepo workspace 原生支持
- **代价**：生态比 Node.js 小，部分 npm 包可能不兼容（至今未遇到）

### 决策 2：为什么用 PostgreSQL + pgvector 而不是专用向量数据库

- **背景**：需要存储访谈片段 + 向量检索，两块数据需要关联查询
- **选项**：
  - A：PostgreSQL + pgvector（关系数据+向量同库）
  - B：PostgreSQL + Pinecone/Weaviate（关系+向量分离）
- **决策**：方案 A
- **理由**：
  - 团队只需维护一个数据库，运维成本低
  - Drizzle ORM 统一管理，不用学两套 API
  - pgvector HNSW 索引在 17K 数据量下性能足够
  - Docker 一行启动
- **代价**：如果未来数据量上百万级可能需要迁移到专用向量库
- **风险**：pgvector 0.8.5 需要在 Mac 上从源码编译，Docker 方式更简单

### 决策 3：为什么用 Hono 而不是 Express

- **背景**：后端 API 需要高性能 + SSE 流式支持
- **选项**：Hono vs Express vs Fastify
- **决策**：Hono
- **理由**：原生 SSE 支持（`streamSSE`），与 Bun 完美配合，TypeScript-first，路由性能优于 Express
- **代价**：社区比 Express 小，但文档质量好

### 决策 4：DeepSeek 作为主 LLM

- **背景**：对话引擎需要一个性价比高的中文大模型
- **选项**：DeepSeek vs GLM-4 vs MiniMax vs GPT-4
- **决策**：DeepSeek-Chat 为主，GLM-4-Flash 为备
- **理由**：
  - 中文能力强，游戏领域知识好
  - API 价格低（约 1 元/百万 token）
  - 支持流式输出（SSE 需求）
  - SDK 封装支持三模型切换，不锁死一家
- **代价**：高峰期可能限流，需要重试机制（已在 `llm.ts` 实现）

### 决策 5：faster-whisper 而不是商用 ASR API

- **背景**：KOL 视频转录需要语音转文字
- **选项**：
  - A：faster-whisper（开源，GPU 本地跑）
  - B：商用 ASR API（讯飞/阿里）
- **决策**：方案 A
- **理由**：
  - 免费，无调用次数限制
  - A6000 GPU 加速后 ~1.3x 实时，可接受
  - medium 模型中文效果够用，large-v2 更好但更慢
- **代价**：需要 GPU 服务器，用 CPU 会非常慢；识别准确率不如商用 API
- **缓解**：HF 镜像解决 HuggingFace 下载问题，多 GPU 并行提速

### 决策 6：KOL 画像用 speechHabits 替代 catchphrases

- **背景**：KOL 数字孪生需要还原 UP 主的说话风格
- **选项**：
  - A：提取口头禅词汇列表（如"坏菜了""带派"），在 Prompt 中列举，让 AI 刻意使用
  - B：用 `speechHabits` 描述整体说话风格（如"略带东北方言，语气戏谑"），让 AI 自然融入
- **决策**：方案 B
- **理由**：方案 A 导致 AI 刻意堆砌词汇（已验证），方案 B 让风格自然流露，用户反馈更好
- **代价**：不能显式展示"这个 UP 主有哪些口头禅"，但对话还原度更高

## KOL 数字孪生专项选型

> 以下内容来自原 `docs/kol/技术选型记录.md`，记录 KOL 分身系统的专项技术决策。

### KOL 决策 1：语言与运行时 — TypeScript (Bun) + 局部 Python

**结论**：主体 TypeScript (Bun + Hono)，embedding 推理侧用 Python (FastAPI + sentence-transformers)

| 方案 | 优点 | 缺点 | 判定 |
|------|------|------|:--:|
| 纯 TypeScript | 架构统一，部署简单 | embedding 模型在 TS 生态无成熟调用方式。transformers.js 需 ONNX 运行时 ~300MB，安装不稳定 | ❌ |
| 纯 Python | embedding/聚类直接调用最成熟的库 | 需另起 Web 框架；团队以 TS 为主 | ❌ |
| **TS 主体 + Python embed 微服务** | 主体架构统一；embedding 用最成熟的 Python 库；Python 侧仅 50 行 FastAPI | 多一个进程要管理 | ✅ |

**实际实现**：TS 侧 Bun + Hono + Drizzle + React + shadcn/ui；Python 侧 FastAPI (`:8765`) + sentence-transformers (bge-large-zh-v1.5)；TS 对话路由通过 `fetch("http://127.0.0.1:8765/embed", ...)` 调用 Python 服务。

### KOL 决策 2：LLM — DeepSeek Chat

**结论**：DeepSeek (`deepseek-chat`)

| 候选 | 优点 | 缺点 | 判定 |
|------|------|------|:--:|
| **DeepSeek** | API 兼容 OpenAI；中文能力强；价格低（¥1/百万 token）；JSON mode 支持好 | 不支持 embedding API | ✅ |
| GLM (智谱) | 支持 embedding API | 提供的 API key 已失效（401） | ❌ |
| MiniMax | 多模态 | 价格较高；本项目不需要多模态 | ❌ |

**实际使用**：对话生成 `deepseek-chat`，SSE 流式，temperature=0.7，max_tokens=2048；画像提取 `deepseek-chat`，JSON mode，temperature=0.3。

### KOL 决策 3：Embedding 模型 — bge-large-zh-v1.5

**结论**：BAAI/bge-large-zh-v1.5（1024 维），通过 ModelScope 镜像下载，Python sentence-transformers 加载

| 候选 | 维度 | 中文效果 | 获取方式 | 判定 |
|------|:---:|:--:|------|:--:|
| **bge-large-zh-v1.5** | 1024 | ⭐⭐⭐ MTEB 中文榜首 | ModelScope 国内镜像（免翻墙） | ✅ |
| bge-small-zh-v1.5 | 384 | ⭐⭐ | 同上 | ❌ 维度不匹配 |
| text-embedding-3-small | 1536 | ⭐⭐ | OpenAI API（需额外 key + 翻墙） | ❌ |
| TF-IDF (纯 JS) | 可变 | ⭐ 词匹配，无语义 | 零依赖 | ❌ 精度不够 |

### KOL 决策 4：向量数据库 — pgvector

**结论**：pgvector（复用现有 PostgreSQL，不加独立向量数据库）

| 候选 | 优点 | 缺点 | 判定 |
|------|------|------|:--:|
| **pgvector** | 与现有 PG 共用；零额外运维；Drizzle ORM 可管理；HNSW 索引查询 <10ms | 大规模（百万级）性能不如 Milvus | ✅ |
| Milvus | 十亿级向量性能最优 | 需独立部署；389 条数据杀鸡用牛刀 | ❌ |
| Chroma | 轻量，Python 原生 | 需另开服务；与现有 PG 架构不统一 | ❌ |

### KOL 决策 5：画像提取 — LLM 直接提取

**结论**：LLM 直接提取（Persona Card + Style Profile），不依赖聚类

KOL 分身与群体画像的核心区别：KOL 是**个体级**（2 个人），群体画像是**群体级**（5-8 种类型）。

| 方案 | 适用场景 | KOL 适用性 |
|------|------|:--:|
| HDBSCAN 聚类 | 从大量样本中自动发现用户类型 | ❌ 只有 2 个人，无法聚类 |
| 人工编写 | 小规模，需要高度准确性 | 🟡 可行但效率低 |
| **LLM 直接提取** | 有大量文本语料，需要结构化画像 | ✅ |

**实际实现**：将每位 UP 主清洗后的语料（~5-13 万字）送入 DeepSeek，JSON mode 输出；Prompt 约束：排除 B 站通用套话，只保留个人独有特征；失败兜底：LLM 不可用时降级为统计方法。

### KOL 决策 6：RAG 检索 — 向量搜索 + ILIKE fallback

**结论**：pgvector 向量相似搜索 + ILIKE fallback

| 方案 | 召回质量 | 实现复杂度 | 判定 |
|------|:--:|:--:|:--:|
| ILIKE 模糊匹配 | ⭐ 词匹配，漏召回严重 | 低 | ❌ |
| **pgvector 向量搜索** | ⭐⭐⭐ 语义匹配 | 中（需 embed 服务） | ✅ |

**实际实现**：主路径：用户问题 → Python embed → pgvector `<=>` 余弦相似 → Top-3；容错路径：embed 服务不可用 → ILIKE fallback；质量控制：自动排除 `ad_label = '广告口播'` 的片段（6 条）。

### KOL 决策 7：广告检测 — 关键词为主

**结论**：关键词快筛（17 个广告品牌/术语关键词），不额外调用 LLM。389 条中检出 6 条广告口播，无漏判。

### KOL 决策 8：部署 — GHCR

**结论**：GHCR (GitHub Container Registry)，`deploy.sh` 执行 rsync → 服务器 `docker build` → `docker compose up -d`。公网地址：`http://49.232.59.125`。
