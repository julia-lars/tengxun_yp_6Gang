# 访谈数据整理计划

> 目标：把 `虚拟用户-笔录 for 元培/` 里的 66 个 docx + 2 个 xlsx，变成 AI 能直接打标的干净文本。

## 本次修订说明

这版对齐了已经定稿的 `apps/api/src/db/schema.ts`（`source_segments` 表 + `respondents` 表），主要改了这几处，其他成员如果看过旧版计划要注意：

- **不再无条件丢弃主持人（Moderator）发言**。旧版"只保留被访者发言"会让很多回答脱离提问语境。现在改成：先识别全部发言，为每条被访者发言找到对应的追问原文存进 `preceding_question`，最终落盘的记录仍然只有被访者这一条，但语境保住了。
- **JSON 格式改了**，字段对齐 schema.ts：`source_file` / `segment_index` / `speaker_id` / `speaker_role` / `preceding_question` / `original_text` / `cleaned_text` / `char_count` / `annotation`。
- **`original_text` 和 `cleaned_text` 是同一条记录里的两个字段**，不是两份文件。`original_text` 提取后不再改动，用于出问题时回溯重跑；`cleaned_text` 清洗前是 null，清洗后才回填，下游查询优先读 `cleaned_text`，读不到退回 `original_text`。
- **人物级别的信息（组别、背景、游戏经验）不进 `annotation`，也不重复塞进每条 segment**。这不再只是一个 JSON 约定，`respondents` 现在是 schema.ts 里的正式表，`(source_file, speaker_id)` 建了唯一索引，用 `speaker_id` 和 `source_segments` 关联。`game`、`category` 这类和具体这条发言绑定的信息才进 `annotation`，不进 `respondents`。
- **同一个 workbook 里不同 sheet 如果确认是同一批受访者，人物级别信息要合并进同一条 respondent 记录**，不要分别产出、导致 `(source_file, speaker_id)` 冲突。判断"是否同一批人"不能只看 `speaker_id` 编号长得像（P1-P15 这种编号在不同 sheet/文件里可能纯属巧合），要有实质内容交叉印证——比如"玩家行为&乐趣整理"和"经验认知乐趣对比"两个 sheet，靠 P1/P6 的画像描述（"不太喜欢对战"/"专家"）和另一个 sheet 里的原话（"不太喜欢跟人对战"/"塔科夫专家"）对得上，才确认是同一批人。确认不了的话，宁可用不同 `source_file` 分开存，不要为了图省事强行合并。**具体怎么拆 `source_file` 见第 3 步的"批次级粒度"** —— 实践下来按批次拆比按 sheet 拆更对，同一个 workbook 里确实可能装着两批毫不相干的受访者。
- **组别代号如果原始数据里带不确定标记（比如"G3?"），原样保留，不要静默"抹平"成确定值**——这种不确定性本身是有效信息，抹掉了后面没法追溯。
- **不是每个 `speaker_id` 都要产出 respondent 记录**：如果确认某个受访者在所有相关 sheet 里都没有任何背景信息（不是"没找到"，是"确认过就是空"），不用为了凑数造一条全 null 的记录，跳过即可，但要在产出说明里注明跳过了哪些人。
- **去重规则收窄了范围**，且改成"丢弃"而不是"合并"，避免破坏 `original_text`/`cleaned_text` 的一对一关系。
- **过短片段过滤不再用固定字符数**，改成占位符判断（`/`、`-`、`无`、`n/a` 这类）。
- 新增了**人工抽样核对**步骤 —— 自动化提取实测中真的抓到过 bug（占位符被误判成有效内容），不能只信自动化结果。

## 分步操作

### 第 1 步：建立文件索引

先不处理内容，把每个文件的基本信息登记好。

**要记录的信息：**
- 文件名、所属研究项目
- 文件类型（docx / xlsx）
- 语言（中文 / 英文 / 中英混合）
- 访谈形式（座谈会 / 深访 / 线上访谈 / 文字转录）
- 预估内容量（段落数、总字数）

**产出：** `data/file_index.csv` — 每行一个文件的基本信息

**怎么让 Claude 做：**

> 遍历 `虚拟用户-笔录 for 元培/` 下所有 docx 和 xlsx 文件。对每个 docx 用 python-docx 读取段落数和总字数；对每个 xlsx 用 openpyxl 读取 Sheet 名称和行列数。把所有信息整理成一个 CSV 文件，保存到 tengxun_yp_6Gang/data/file_index.csv。

### 第 2 步：处理 docx 文件

66 个 docx 文件逐个处理。每个文件的结构不同（有的是 Q&A 对话体，有的是连续叙述），需要分两步：

#### 2a：提取纯文本

- 用 python-docx 提取所有段落
- 保留段落之间的换行
- 去掉页眉页脚、页码等非正文内容

#### 2b：按说话人分片 + 保留提问语境

docx 里的对话格式大致是：

```
Moderator: 你平时玩什么射击游戏？
张三: 主要是 CS 和 Valorant。
Moderator: 为什么喜欢这两款？
张三: 因为枪法要求高，打赢很有成就感。
```

处理逻辑：

1. 先把 Moderator 和被访者的发言都识别出来，标记 `speaker_role`
2. 对每一条被访者发言，找最近的一条 moderator 发言，把它的原文抽出来存进 `preceding_question`（如果紧邻的上文就是被访者自己接着说的，或者压根没有 moderator 提问，`preceding_question` 就是 `null`）
3. **最终落盘的记录只保留被访者的发言**（`speaker_role` 固定是 `interviewee`），moderator 的原话不单独存成一行——但因为提问语境已经进了 `preceding_question`，信息不算丢失
4. 如果以后需要完整还原对话流（不只是当画像证据用），再考虑把 moderator 也存成单独行，用 `speaker_role` 区分（schema.ts 已经支持这种扩展，`speaker_role` 是 enum 不是写死的布尔值）

**产出：** `data/segments/` 目录，每个 docx 对应一个 JSON 文件：

```json
[
  {
    "source_file": "美国HD端用户生态与决策链路研究/座谈会笔录-G1（放松向）.docx",
    "segment_index": 3,
    "speaker_id": "Jordan K.",
    "speaker_role": "interviewee",
    "preceding_question": "What do you usually use shooting games for?",
    "original_text": "I mostly play Call of Duty, just to relax after work...",
    "cleaned_text": null,
    "char_count": null,
    "annotation": {}
  }
]
```

> `cleaned_text` / `char_count` 这一步先留空，第 4 步清洗时回填到**同一条记录**里，不生成新文件。

**怎么让 Claude 做：**

> 处理 `虚拟用户-笔录 for 元培/` 下的所有 docx 文件。对每个文件：用 python-docx 提取段落文本，识别 Moderator 和被访者的发言交替模式，标记 speaker_role。对每条被访者发言，取最近一条 moderator 发言的原文作为 preceding_question。最终输出只保留被访者发言，按段落分片。每个文件输出一个 JSON 文件，保存到 tengxun_yp_6Gang/data/segments/。格式：{ source_file, segment_index, speaker_id, speaker_role, preceding_question, original_text, cleaned_text: null, char_count: null, annotation: {} }。speaker_id 用文档里出现的说话人标识（真实姓名或编号），同一文件内保证唯一即可，不需要跨文件保持一致。

2 个 xlsx 文件结构复杂，需要先按 Sheet 的用途分类，不是每个 Sheet 都要转成 segments。

**枪战类长线新手体验研究/用户记录表.xlsx**（共 11 个 Sheet）：

| Sheet | 用途分类 | 处理方式 |
|---|---|---|
| 玩家行为&乐趣整理 | 内容（含被访者原话） | ✅ 已转 segments（365 条）+ respondents |
| 经验认知乐趣对比 | 内容（含被访者原话） | ✅ 已转 segments（90 条）+ respondents |
| ABIvsDF记录表 | 内容（含被访者原话） | ✅ 已转 segments（374 条）+ respondents |
| 特征诉求 | 内容，但**只有人物级别摘要 + 研究员分析** | ✅ 已核实：不产 segments，只贡献 respondents 字段（见下方"特征诉求的处理结论"） |

| ABIvsDF新手访谈大纲、访谈大纲（中文）、Manuscript (EN) | 大纲，无被访者回应 | ✅ 已核实，不处理 |

对于"玩家行为&乐趣整理"和"经验认知乐趣对比"这两个已经核实过结构的 Sheet（合并单元格、ABC 三层分类、隐藏列、game1/game2 两个对局 slot 等），已经写好并验证过专用脚本。"ABIvsDF记录表"和"特征诉求"同样已逐格核实（行号→类目映射、A/B 列合并范围、占位符），产出已通过双向校验：有效单元格与 segments 条数一一对应，每条 `annotation` 与其所在行的 A/B 列自洽。

**这个 workbook 里装了两批完全不同的受访者**，处理时按批次区分：

| 批次 | 受访者 | 被测游戏 | 来源 Sheet |
|---|---|---|---|
| EFT | P1-P13，塔科夫老玩家（美国） | 逃离塔科夫 / DMZ 等 | 玩家行为&乐趣整理、经验认知乐趣对比 |
| ABIvsDF | P1-P8，枪战类玩家（国内，CS/瓦/PUBG/CF 背景） | 三角洲行动 / 暗区突围 | ABIvsDF记录表、特征诉求 |

两批的 `speaker_id` 都是 P1、P2… 但**编号撞车纯属巧合，不是同一批人**。

后续遇到结构类似的 Sheet，参照这两个脚本的做法，核心原则是**人物级别的信息和发言级别的信息要分开产出**：

- 人物级别（组别、画像、游戏经验）：每个人只记一次，对齐 schema.ts 的 `respondents` 表（`source_file` / `speaker_id` / `display_name` / `group_code` / `background` jsonb），用 `speaker_id` 关联。EFT 批的"玩家行为&乐趣整理"和"经验认知乐趣对比"经交叉核对确认是同一批 P1-P13（P14/P15 两边都没有背景信息，不产出记录），合并成一份；ABIvsDF 批的"ABIvsDF记录表"和"特征诉求"同理合并成一份。产出见 `data/sheets_data/respondents_*.json`
- 发言级别的结构信息（对应哪个 game、哪一类 category、第几层分类、第几轮对局）：放进 `annotation` 字段，不要拍平丢弃。`game`/`category` 不作为 `source_segments` 表的正式列（已经抽样过 68 个文件里的实际数据，这类信息在不同来源里体现不一致，且和"游戏无关的泛化画像"这个项目目标冲突），只作为 `annotation` 里的半结构化内容。产出见 `data/sheets_data/segments_*.json`（"经验认知乐趣对比"已经把"游戏经验情况"这个伪 game 值的行排除，因为那部分内容是人物级别的背景介绍，已经进了 respondents 的 `game_experience_summary`）

#### `source_file` 用批次级粒度

```
枪战类长线新手体验研究/用户记录表.xlsx#EFT
枪战类长线新手体验研究/用户记录表.xlsx#ABIvsDF
```

不是 workbook 级（那样两批人会混在一起查出来），也不是 sheet 级（一条 respondent 的背景来自多个 sheet，sheet 级会切断它与另一个 sheet 的 segments 的关联）。具体来自哪个 sheet 记在 `annotation.sheet` 里，信息不丢。因为 `source_file` 已经把两批人分开，`speaker_id` 直接用 P1-P8 / P1-P13，不需要加前缀。

> 这一条取代了本文档早期版本的建议（"确认不了是否同一批人就把 sheet 名拼进 source_file 分开存"）。实践中发现真正需要区分的是**批次**而不是 sheet —— 按 sheet 拆会把同一批人的 respondent 和 segments 割断。

#### `annotation` 字段约定

- **值为 null 的键不输出**，不写 null 占位
- `games` / `game_codes`：游戏名用中文全名（`三角洲行动` / `暗区突围` / `逃离塔科夫`），原始代号留在 `game_codes` 便于回溯。同时评价两款游戏的环节 `games` 就是两个元素；与被测游戏无关的环节（如测试前的过往经验摸底）用空列表，区别于"未知"
- `category_l1` / `category_l2` / `session_order`：三个 segments 文件共用同一套字段名。`session_order` 表示同一场景的第几轮对局
- ~~`round_label`~~：已废弃。原是"玩家行为&乐趣整理"的专用字段（值形如 `EFT - PVE - R1`），套到别的 sheet 上会大量为 null，且同时承载"地图+轮次"和"观察第几轮"两种语义，已拆成 `category_l1` + `session_order`
- 观察员补充笔记是"关于该玩家"的行为观察而非玩家原话，`speaker_role` 标 `moderator`，但保留 `speaker_id` 以便按玩家检索其行为证据，`annotation.type = observer_note` 标明来源

#### 特征诉求的处理结论

该 sheet 逐行核实后的构成：

- 元信息行（玩家编号 / 录像链接 / 玩家属性 / 游玩顺序 / 测试时间）→ 进 respondents
- 行为特征、主要诉求的逐人摘要 → 进 respondents
- 跨玩家的**研究员分析结论**（如"P1P2 属于能快速建立游戏目标型"）→ 存进 `analysis_notes_用户记录表_特征诉求.json`，**不进 segments**。把结论喂进 `source_segments` 参与画像聚类等于让 AI 去"发现"人已经写好的答案，属于循环论证；留作对照/验证材料
- DF / ABI 的 UX 缺陷清单（序号 + 环节模块 + 问题描述）→ 产品侧问题，无 speaker 归属，与玩家画像任务无关，**舍弃不产出**

所以它是**纯 respondents 来源**，segments 贡献为 0。这也是一条通用经验：**"含被访者相关内容"不等于"能产 segments"** —— 判断标准是这段文字是不是被访者自己的表达，研究员的归纳结论不算。

⚠️ **分析笔记里的编号不是玩家编号。** 那些 `1. 2. 3.` 是类型序号，每条后面自己挂着对应哪些玩家（实际是 1.→P1P2、2.→P3P7、3.→P6、4.→P7、5.→P6、6.→P4，P6 出现两次，P5/P8 一次没出现），已解析进 `mentioned_speaker_ids`。**不要按 1↔P1 的位置映射去理解**（8 条里会错 6 条）。同理，另外几格的编号完全没有玩家标记，是设计问题归因，不是玩家清单。

#### 组别代号的适用范围

`group_definitions.json` 来自"样本条件（中英）"，定义的是**美国受访者 + 逃离塔科夫**（如 G2 初学组要求"近 1 年内开始玩塔科夫、累计 100-500h"）。

**它只适用于 EFT 批。** ABIvsDF 批是中国玩家，核对其"EFT品类游戏经验摸底"后确认：4 个 G2 里 P3「听说过塔科夫…不想了解」、P5「听过塔科夫」、P6「听过塔科夫，没玩过」，**没有一个符合初学组条件**。该批的 G1/G2 是另一套批次内部编号，已在 respondents 的 `background.group_code_scope` 显式标注，查询时不要跨批次比较。

**生存撤离类新手引导体验研究/整合记录表.xlsx：** 结构还没有像上面两个 Sheet 一样逐格核实过，处理前需要先重复"合并单元格 + 分类列"的人工核实步骤，不要直接照搬枪战类那份的列位置假设。

**产出：** 均在 `data/sheets_data/`（不是计划早期写的 `data/segments/`、`data/respondents/`）
- `segments_用户记录表_*.json` —— 和 docx 输出同一套字段
- `respondents_用户记录表_*.json` —— 对齐 `respondents` 表；同一批人的多个 sheet 合并成一份，不要分别产出导致 `(source_file, speaker_id)` 冲突
- `analysis_notes_用户记录表_特征诉求.json` —— 研究员分析结论，不入库，留作对照
- `group_definitions.json` —— 组别代号定义（已完成）

**怎么让 Claude 做：**

> 先打开这两个 xlsx 文件，列出所有 Sheet 名称，对每个 Sheet 判断属于"内容""参考""规划""大纲无回应"里的哪一类，把判断结果发给我确认，不要自行假设。注意"含被访者相关内容"不等于"能产 segments"——研究员归纳的结论、产品侧问题清单都不是被访者原话。确认后，对内容类 Sheet 参照已有脚本的做法分别产出 segments 和 respondents 两类 JSON；对参考类 Sheet 产出小型独立 JSON 文件。提取脚本放在仓库外，避免影响组内其他成员。

### 第 4 步：数据清洗

文本提取出来后，做一轮基础清洗，清洗结果直接写回**同一条记录**的 `cleaned_text` 和 `char_count` 字段（`original_text` 保持不变）。

#### 4a：去重

范围限定在**同一 `speaker_id` + 同一语境**内（语境指 `annotation` 里 `game`/`category` 一致，或者同属一个 docx 文件），相邻/相近位置的片段内容相似度 > 90% 时，保留信息量更完整的一条，**直接丢弃**另一条——不做文本合并，避免破坏 `original_text`/`cleaned_text` 的一对一关系。

#### 4b：文本清理

- 去口语填充词：英文去掉 "um, uh, you know, like, I mean" 等，中文去掉 "那个、就是、怎么说呢" 等（不要太激进，稍微去一下即可）
- 去除过短/无意义的片段：不用固定字符数一刀切，改成占位符判断——过滤纯空白、以及 `/`、`-`、`无`、`无内容`、`n/a`、`、` 这类占位符（参考 `convert.py` 里的 `is_meaningful()`）。中文短句信息密度高，20 字符这种固定阈值容易误伤"是的，确实这样"这类有意义的简短表态

> 注：不需要单独"去除纯 Moderator 引导语"这条规则了——moderator 内容在第 2 步就已经不进入最终记录。

#### 4c：人工抽样核对

清洗完成后，从每个来源项目里抽样核对至少几条记录，重点看这几个最容易出自动化 bug 的地方：speaker_role 有没有分错、preceding_question 有没有对应错、去重有没有误删。这一步不能省——实测 `convert.py` 时就真的抓到过占位符被误判成有效内容的 bug，纯自动化流程不保证可靠。

**产出：** `data/segments_cleaned/` — 和 `data/segments/` 里同样的记录，`cleaned_text`/`char_count` 已回填，去重后记录数可能减少

**怎么让 Claude 做：**

> 读取 data/segments/ 下的所有 JSON 文件，做数据清洗：在同一 speaker_id + 同一语境范围内，去重（相似度 > 90% 的相邻片段丢弃信息量较少的一条）、去口语填充词、用占位符判断去除无意义片段。清洗结果写回同一条记录的 cleaned_text 和 char_count 字段，保存到 data/segments_cleaned/。

### 第 5 步：合并与统计

把所有清洗后的片段合并成单一文件，做统计分析：

- 总片段数
- 每个研究项目的片段数
- 中英文各多少
- 平均片段长度
- 说话人数量分布

**产出：** `data/all_segments.jsonl` — 一行一个片段，完整的待打标数据集

**怎么让 Claude 做：**

> 把 data/segments_cleaned/ 下所有 JSON 合并成一个 JSONL 文件 data/all_segments.jsonl。然后统计：总片段数、按研究项目的分布、中英文分布、平均片段长度、说话人数量。统计结果保存到 data/segments_stats.md。

## 注意事项

- 搜打撤品类研究/海外有 8 组中英文对照文件（`xxx-中文版.docx` 和 `xxx-英文原版.docx`），处理时优先用中文版，英文原版留作对照
- 漫威争锋的 2 个"文字转录"文件可能格式特殊（不是对话体而是连续叙述），需要单独处理
- 美国 HD 端用户生态研究的 4 个文件已经按用户类型分好了（放松/竞技/社交/叙事），这个标签要保留在 `source_file` 字段里
- 输出全部用 UTF-8 编码
- **speaker_id 命名体系在不同来源之间不统一**：同一个人在不同 Sheet/文件里可能有不同编号（比如"用户列表"用 G3-P1 这种编码 + 真实英文名，"玩家行为&乐趣整理"用 P1-P15），`speaker_id` 只保证同一个 `source_file` 内唯一，**不要假设跨文件可以直接拿 speaker_id 关联**，除非先人工确认过是同一批受访者。用户记录表.xlsx 里已经实证了这一点：EFT 批和 ABIvsDF 批都从 P1 开始编号，但是两批毫不相干的人
- "用户列表"里的受访者人口学要求（白种人:其他=7:3，明显针对美国受访者）和哪一批 P 编号对应，目前还没有确认，处理这份数据前需要先跟了解背景的同事对一下。已知它**不对应 ABIvsDF 批**（那批是中国玩家）
- **组别代号也不能跨批次比较**：`group_definitions.json` 的 G1/G2/G3 定义针对美国受访者 + 逃离塔科夫，ABIvsDF 批虽然也写 G1/G2，但是另一套批次内部编号，实测其 4 个 G2 无一符合定义里的"初学组"条件。跨来源比较组别前先确认定义是否同源
