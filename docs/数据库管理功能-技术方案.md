## 一、需求分析

### 1.1 当前现状

| 维度 | 现状 |
|------|------|
| **数据库** | PostgreSQL 16 + pgvector，Drizzle ORM，9 张表（含 3 张教程遗留表） |
| **数据存储** | `data/` 目录下有大量 JSON 文件（~20GB），部分已入库、部分未入库 |
| **数据入库方式** | 仅通过流水线脚本（`scripts/load_segments.py`）或 API Pipeline（`POST /api/pipeline/start`） |
| **数据管理** | 无可视化界面，只能通过 `pgweb`（端口 8081）或 SQL 命令行操作 |
| **已入库数据** | `source_segments`（17K+）、`respondents`、`personas`（4 条手写）、`kol_profiles`（2 条）、`kol_segments`（389 条） |
| **未入库数据** | `data/群体画像/` 下的 `segments_*.json` / `respondents_*.json`、`data/annotated/` 下的标注后数据 |

### 1.2 需求拆解

1. **数据库 CRUD 管理界面**：对核心表（`source_segments`、`personas`、`respondents`、`kol_profiles`、`kol_segments`）提供查看、修改、删除、新增功能
2. **存量数据导入**：将 `data/` 目录下已有的 JSON 文件批量导入对应的数据库表
3. **流水线数据入库**：数据流水线（Pipeline）处理后的数据自动写入数据库（已有 `pipeline-db.ts`，需完善）

### 4.2 数据导入 API（`/api/import`）

| 方法 | 路径 | 说明 |
|------|------|------|
| `POST` | `/api/import/json` | 上传 JSON/JSONL 文件导入 |
| `POST` | `/api/import/from-data-dir` | 从 `data/` 目录直接导入（服务端操作） |
| `GET` | `/api/import/jobs` | 导入历史列表 |
| `GET` | `/api/import/jobs/:id` | 导入作业详情 |
| `POST` | `/api/import/dry-run` | 预检：检查文件格式、字段映射、重复数据 |

**导入策略**：

| 策略 | 说明 | 适用场景 |
|------|------|------|
| `upsert` | 按唯一键判断：存在则更新，不存在则插入 | `respondents`（`source_file, speaker_id` 唯一） |
| `insert-only` | 只插入不更新，跳过重复 | `source_segments`（无唯一业务键） |
| `replace` | 清空目标表后全量导入 | 小表初始化 |
| `append` | 追加导入，不管重复 | 增量数据 |

### 4.3 流水线增强（完善现有 `/api/pipeline`）

当前流水线 `POST /api/pipeline/start` 已支持：
- 上传 → 提取 → 清洗 → AI 打标 → 向量嵌入 → 写入数据库

需要增强的点：

| 增强项 | 说明 |
|------|------|
| **断点续跑** | 流水线中断后，从上次完成的阶段继续，不从头开始 |
| **单阶段执行** | 支持只执行清洗/只执行打标/只执行嵌入，不强制从头跑 |
| **入库结果回执** | 写入数据库后返回具体的 `inserted` / `updated` / `skipped` 数量 |
| **数据源选择** | 支持从 `data/` 目录选文件作为输入，替代必须上传 |

└──────────────┘    └──────────────┘    └──────────────┘

### 5.3 关键实现细节

**source_segments 导入**：
- 字段映射：`source_file` → `sourceFile`, `cleaned_text` → `cleanedText`, `char_count` → `charCount`
- 若同一文件已存在数据，先 DELETE 再 INSERT（按 `source_file` 匹配）
- embedding 向量字段暂不导入（需重新 embed）

**respondents 导入**：
- 唯一键：`(source_file, speaker_id)`
- 采用 upsert 策略：`ON CONFLICT (source_file, speaker_id) DO UPDATE`
- `background` 字段（jsonb）需要与原 Schema 对齐

**personas 导入**：
- 当前只有 4 条手写种子数据
- 导入源：聚类脚本 `scripts/cluster_personas.py` 产出

## 八、安全性考虑

| 维度 | 措施 |
|------|------|
| **SQL 注入** | Drizzle ORM 参数化查询，天然防注入 |
| **权限控制** | 当前无认证系统，管理接口暂不对外开放；后续加 JWT + RBAC |
| **数据校验** | 使用 Zod Schema 校验输入（复用 `@app/shared` 的类型定义） |
| **操作审计** | `audit_log` 表记录所有 CUD 操作 |
| **软删除** | `source_segments` 加 `deleted_at` 字段，删除操作改为软删除 |
| **批量操作限制** | DELETE/UPDATE 必须带 WHERE 条件，禁止全表操作 |
| **速率限制** | 导入接口加并发限制，防止打爆数据库 |

## 十、关键技术决策

| 决策点 | 选择 | 理由 |
|------|------|------|
| **CRUD 代码复用** | 工厂函数模式 | 多张表结构相似，避免重复写 5 份 CRUD 代码 |
| **导入分批大小** | 500 条/批 | 平衡内存占用和 DB 连接效率 |
| **删除策略** | 软删除（`deleted_at`） | 数据可恢复，符合审计要求 |
| **JSONB 字段编辑** | 代码编辑器组件 | `annotation` 等字段是嵌套 JSON，普通 input 无法编辑 |
| **前端表单渲染** | 基于 Schema 动态渲染 | 表结构变更时不需要改前端代码 |
| **管理界面路由** | `/admin/*` 独立路由 | 与现有 `/personas` `/kol` 等业务路由隔离 |
| **导入日志存储** | 新表 `import_jobs` | 可追溯每次导入的历史记录 |

## 十一、风险与注意事项

1. **大文件导入**：`segments_竞技品类基础研究.json`（4.7MB）单文件含数千条记录，需分批处理 + 进度反馈
2. **向量字段**：`embedding` 列（1024 维浮点数组）不可直接编辑，导入时需跳过或重新 embed
3. **数据一致性**：`personas.evidence_ids` 引用 `source_segments.id`，删除 segment 时需检查引用
4. **现有数据**：`data/` 目录下部分数据已入库，导入前需检测重复，避免重复插入
5. **性能**：17K+ 条 `source_segments` 的列表查询需要分页 + 索引优化（已有 `source_file` 和 `speaker_id` 索引）
6. **无认证**：当前系统无登录机制，管理接口暂不暴露到生产环境，仅开发环境使用
