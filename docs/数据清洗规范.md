## 1. 最高优先级原则

以下原则为本文档的最高优先级规则。**下游任何具体规则与此冲突时，以下游规则服从本原则。**

### 1.1 P0：数据保留原则

**保留与用户游戏行为、体验、偏好、动机、决策及其上下文存在直接关系的信息。**

因此：

- 不能仅因为文本短就删除
- 不能仅因为是自我介绍就删除
- 不能因为是口语表达就大幅重写
- 不能因为是重复信息就直接删除原始 Segment（标记 `removed_duplicate` 即可）

### 1.2 P1：原文永久保留

`original_text`：

> **永远保持原语言、原内容，不允许修改，不允许删除。**

即使一个 Segment 被判定为噪声：

```json
{
  "original_text": "嗯嗯。",
  "cleaned_text": null,
  "char_count": 0,
  "cleaning_status": "removed_noise"
}
```

它仍然保留在数据库中，而不是被物理删除。

### 1.3 AI 执行约束

以下为模型在清洗执行过程中的**禁止行为清单**。这些约束优先级高于任何具体清洗规则。

**模型不得：**

| # | 禁止行为 | 说明 |
|:--:|------|------|
| 1 | 修改 `original_text` | 任何情况下不得改动 |
| 2 | 根据 `preceding_question` 补写用户没有说过的信息 | 例如不能把"因为枪感好"写成"因为Apex的枪感好" |
| 3 | 删除因果/转折/态度/不确定性词 | 因为、所以、但是、感觉、觉得、可能、应该等 |
| 4 | 把体验/偏好/态度写入 Profile | "我觉得XX枪感好"留在 Segment，不进入档案 |
| 5 | 根据常识推断年龄、职业、游戏经历 | 用户没说就不填 |
| 6 | 把"可能玩过"改成"玩过" | 不改变确定性程度 |
| 7 | 把"我觉得"改成事实陈述 | 不改变主观/客观属性 |
| 8 | 为了减少 `needs_review` 而强制判定 `kept` | 不确定就是不确定 |
| 9 | 进行语义去重 | 清洗阶段不做语义相似度去重 |
| 10 | 将多个 Segment 合并成一个 Segment | 每个 Segment 独立处理 |
| 11 | 把 `preceding_question` 的内容拼入 `cleaned_text` | 上下文 ≠ 用户内容 |
| 12 | 在翻译中删除表示程度/态度/不确定性的修饰词 | "way more" → "强很多"，不是"强" |

### 1.4 P2：清洗不是重写

> **清洗不是"把文本变得更漂亮"，而是"在不改变用户原始语义的前提下，去除真正无价值的噪声，并把文本整理成适合后续标注和 Embedding 的形式"。**

因此：

- 宁可保留一句不完美的话，也不要为了干净而损失用户的行为、体验、偏好、动机、决策或上下文
- 清洗阶段不进行 Fact 提取、Fact 拆分、Fact 聚合或因果重组
- 清洗只负责让文本"可用"，不负责解释文本

### 1.5 P3：语言规则

| 字段 | 数据库 | 文件输出 | 说明 |
|------|:---:|:---:|------|
| `original_text` | **原语言** | **不输出** | 永久不变，数据库保留 |
| `cleaned_text` | **中文** | **中文** | 轻度翻译 + 轻度口语整理，不是语义重写 |
| `preceding_question` | **原语言** | **中文** | 数据库保留原语言；文件输出时翻译为中文 + 轻度标准化 |
| `Profile` 内文本字段 | **中文** | — | 英译中 |
| `Gaming Background` 内文本字段 | **中文** | — | 英译中，游戏名统一用中文标准名 |
| `self_intro_raw` / `gaming_self_intro_raw` | **原语言** | — | raw 字段保持原文 |
| `preceding_question`（数据库） | **原语言** | — | 上下文，不参与 Segment 字数统计，不作为 Segment 清洗的修改对象 |

### 1.6 P4：自我介绍 ≠ 档案

> **不要因为信息出现在"自我介绍"里，就认为它一定是档案。**

一段自我介绍可能同时包含：

- 档案信息（年龄、职业）→ `Profile`
- 游戏背景（当前游戏、平台、时长）→ `Gaming Background`
- 体验/偏好/态度（"我觉得XX枪感好"）→ 保留在 Segment，**不进入档案**

## 2. 设计目标

### 2.1 清洗定位

```
数据提取（数据提取规范 v1.2）  →  数据清洗（本文档）  →  数据标注（数据标注标准文档 v2.1）
       │                              │                          │
  source_segments               cleaning_status              annotation (jsonb)
  cleaned_text = null           cleaned_text / char_count     AI 打标 / 人工标注
  cleaning_status = null        填充
```

清洗是提取和标注之间的桥梁。提取阶段产出的 `original_text` 是"原文搬运"，`cleaned_text` 和 `cleaning_status` 均为 null；清洗阶段负责：

1. 判定每个 Segment 的有效性（kept / removed_*）
2. 对有效 Segment 做轻度文本标准化
3. 将 `cleaned_text` 转为中文
4. 检测并标记明显重复
5. 从自我介绍 Segment 中提取档案信息，合并到 `respondents` 表
6. 清洗参与者档案文本

**清洗阶段明确不做**：
- Fact 提取、拆分、聚合或因果重组
- 大规模语义改写
- 从非自我介绍 Segment 提取档案信息
- 物理删除任何 Segment

### 2.2 三个层级：数据库保留 ≠ 清洗有效 ≠ 进入下游

以下三个概念必须严格区分：

| 层级 | 含义 | 处理 |
|------|------|------|
| **数据库保留** | 所有 Segment 的 `original_text` 永久存储 | 100% 保留，不做物理删除 |
| **清洗有效** | `cleaning_status` 判定为 `kept` | 有 `cleaned_text`，进入清洗结果文件 |
| **进入下游** | 读取清洗结果 JSON 文件 | 标注、Embedding 直接消费文件 |

`removed_noise`、`removed_flow`、`removed_duplicate`、`removed_irrelevant` 的 Segment **不进入输出文件**，但数据库保留原样。

`needs_review` 的状态流转：

```
needs_review → 进入清洗结果文件 → 人工复核 → 重新判定 cleaning_status → 通过后保留在清洗结果文件
```

**`needs_review` 的 Segment 不能直接进入 Annotation / Embedding，必须先经人工复核。**

### 2.3 核心概念：单一清洗结果文件

本版本输出**单一 JSON 文件**，不再区分 `cleaned/` 与 `review/` 目录。文件结构为：

```
{
  "source_file": "...",
  "respondents": [...],      // 清洗后的参与者档案
  "segment_count": 46,
  "segments": [...],         // kept + needs_review
  "summary": {...}
}
```

**数据库层面**：所有 Segment 保留在 `source_segments` 表中，通过 `cleaning_status` 标记状态（审计用途）。

```
                    ┌─ kept ───────────────→ cleaned_text 已填充，进入清洗结果文件
原始 Segment ───────┤
                    ├─ removed_noise ──────→ cleaned_text = null, 不输出文件，数据库保留
                    ├─ removed_flow ───────→ cleaned_text = null, 不输出文件，数据库保留
                    ├─ removed_duplicate ──→ cleaned_text = null, 不输出文件，数据库保留
                    ├─ removed_irrelevant ─→ cleaned_text = null, 不输出文件，数据库保留
                    └─ needs_review ───────→ cleaned_text 已填充，进入清洗结果文件（待复核区）
```

> **设计意图**：`cleaning_status` 降级为审计字段，不作为下游筛选依据。下游逻辑简化为：**读取清洗结果文件 = 有效数据 + 待复核数据**。

### 2.4 数据层级关系

```
source_segments (提取阶段产出)
      │
      ├── original_text (原始文本，永久保留，不可变)
      ├── cleaned_text (清洗阶段写入，初始为 null)
      ├── char_count (清洗阶段写入，初始为 null)
      ├── cleaning_status (清洗阶段写入，初始为 null)
      │
      ▼
清洗流水线
      ├── ① Segment 有效性判定 → cleaning_status（临时）
      │   ├── 确定性噪声    → removed_noise
      │   ├── 纯流程对话    → removed_flow
      │   ├── 游戏无关内容  → removed_irrelevant
      │   ├── 有效内容      → kept（不再按字数细分 kept）
      │   └── 无法确定      → needs_review
      ├── ② 文本轻度标准化
      ├── ③ 中文化
      ├── ④ 明显重复检测
      ├── ⑤ 自我介绍数据提取 → 合并到 respondents
      ├── ⑥ 参与者档案清洗
      └── ⑦ 文件输出
      │
      ▼
source_segments (清洗后 — 所有原始 Segment 仍在数据库)
      ├── original_text (不变)
      ├── cleaned_text (kept/needs_review 的已填充，removed_* 的为 null)
      ├── char_count (kept/needs_review 的已填充，removed_* 的为 0)
      ├── cleaning_status (已填充，审计用途)
      │
      ▼
文件系统输出
      └── {source_file}_cleaned.json  → kept + needs_review + respondents + summary
      │
      ▼
respondents (参与者档案 — 清洗后)
      ├── profile (中文，自我介绍提取 + 文本清洗 + 字段校验)
      ├── gaming_background (中文，游戏名用中文标准名)
      └── background (原始背景信息，清洗后)
```

## 3. 清洗流水线总览

### 3.1 流水线阶段

```
① 原始 Segment 完整保留
        ↓
② Segment 有效性判定 → cleaning_status（临时）
   ├── 明确噪声    → removed_noise
   ├── 明确流程话术 → removed_flow
   ├── 有效游戏相关内容 → valid（临时标记，待清洗后细分 kept）
   └── 无法确定    → needs_review
        ↓
③ 文本轻度标准化（对 kept / needs_review 的 Segment 及 preceding_question）
   ├── 去首尾空格
   ├── 合并异常空格
   ├── 轻度标点规范
   └── 去无语义填充词（仅开头，且不改变语义）
        ↓
④ 中文化（对 kept / needs_review 的 Segment 及 preceding_question）
   └── cleaned_text / preceding_question → 中文
        ↓
⑤ 按 cleaned_text 字符数细分 kept / kept
   ├── ≥ 15 字符 → kept
   └── < 15 字符 → kept
        ↓
⑥ 明显重复检测（在 cleaned_text 上执行）
   ├── 完全重复 → cleaning_status = "removed_duplicate"
   └── 近乎逐字复制（且非信息超集）→ cleaning_status = "removed_duplicate"
        ↓
⑦ 自我介绍信息提取（结构化档案提取，不属于 Segment Cleaning 本身）
   ├── Profile 提取
   └── Gaming Background 提取
        ↓
⑦ Profile / Gaming Background 清洗
   ├── 中文化
   ├── 轻度文本清理
   ├── 游戏名标准化为中文
   └── 字段级合理性校验
        ↓
⑨ 输出 Cleaning Status（写入数据库）
        ↓
⑨ 文件输出
   └── {source_file}_cleaned.json  ← respondents + kept + needs_review + summary
```

### 3.2 执行顺序

```
① 完整保留 → ② 有效性判定 → ③ 轻度标准化 → ④ 中文化 → ⑤ 去重 → ⑥ 自我介绍提取 → ⑦ 档案清洗 → ⑧ 写入数据库 → ⑨ 文件输出
```

原因：
- 有效性判定必须在标准化之前，避免无效内容被"洗成有效"
- 标准化必须在去重之前，否则相同内容因空格/标点差异逃过去重
- kept 细分必须在标准化和中文化之后，因为判定依据是 `cleaned_text` 的字符数
- 去重在 `cleaned_text` 上执行，确保同一内容的不同表达形式能被识别
- 自我介绍提取依赖清洗后的 Segment，在 Segment 清洗完成后执行
- 档案清洗在自我介绍提取之后执行，确保新合并的文本也经过清洗
- 文件输出在数据库写入之后执行，确保文件内容与数据库一致

> **注意**：§8「自我介绍数据提取与合并」属于**结构化档案提取**，不属于 Segment Cleaning 本身。仅因其输入依赖清洗后的 Segment，故在本 Pipeline 中编排执行。这不与"清洗阶段不做 Fact 提取"产生概念冲突。

## 4. Segment 有效性判定

### 4.1 输入格式

清洗的输入是提取阶段产出的 Segment，字段定义来自《数据提取规范》§6.6：

```json
{
  "source_file": "研究项目/文件名.docx",
  "segment_index": 3,
  "speaker_id": "P001",
  "speaker_role": "interviewee",
  "preceding_question": "大家介绍一下自己的游戏经历… → 你觉得自己是MOBA玩家还是射击游戏玩家？",
  "original_text": "可能偏射击。",
  "cleaned_text": null,
  "char_count": null,
  "cleaning_status": null
}
```

**关键约束**：
- 只处理 `speaker_role = "interviewee"` 的片段
- `speaker_id = "unknown"` 的片段已在提取阶段排除
- `original_text` 永远不变
- `cleaned_text`、`char_count`、`cleaning_status` 初始为 null，由清洗阶段写入
- **所有 Segment 始终保留在数据库中，不做物理删除**

### 4.2 preceding_question 使用约束

`preceding_question` 是对话上下文，不是用户内容。使用时必须遵守：

| 允许 | 禁止 |
|------|------|
| 用于判断 Segment 是否有上下文依赖 | 拼入 `cleaned_text` |
| 用于判断是否属于自我介绍 | 翻译后拼入 `cleaned_text` |
| 用于去重分组 | 用于补充用户没说过的信息 |
| 用于辅助理解模糊回答 | 参与字数统计 |

**文件输出时的处理**：

`preceding_question` 在数据库中以原语言保留，不翻译、不清洗。但在文件输出（`cleaned/`、`review/`）中，`preceding_question` 需翻译为中文并轻度标准化，规则如下：

| 步骤 | 操作 |
|:---:|------|
| 1 | 去除首尾空白 |
| 2 | 合并多余空格 |
| 3 | 合并连续标点 |
| 4 | 英文提问 → 翻译为中文（按 §6.2 中文化原则） |
| 5 | 中文提问 → 仅做步骤 1-3，不翻译 |

> **注意**：文件输出中的 `preceding_question` 清洗是**独立于 Segment 清洗**的操作。它不影响 Segment 有效性判定，也不影响 `cleaned_text` 的内容。数据库中的 `preceding_question` 始终保持原语言不变。

**典型错误**：

```
❌ preceding_question: "你为什么喜欢Apex？"
   original_text: "因为枪感好。"
   cleaned_text: "因为Apex的枪感好。"  ← 模型自己补充了"Apex"，用户没说过

✅ preceding_question: "你为什么喜欢Apex？"
   original_text: "因为枪感好。"
   cleaned_text: "因为枪感好。"        ← 正确，保留用户原话
```

### 4.3 cleaning_status 值域

| 状态 | 含义 | cleaned_text | char_count | 后续处理 |
|------|------|:---:|:---:|------|
| `kept` | 有效，进入下游 | 已填充 | > 0 | 标注、Embedding |
| `removed_noise` | 确定性噪声 | null | 0 | 不进入标注/Embedding |
| `removed_flow` | 纯流程对话 | null | 0 | 不进入标注/Embedding |
| `removed_duplicate` | 重复片段 | null | 0 | 不进入标注/Embedding |
| `removed_irrelevant` | 与游戏无关的非噪声内容 | null | 0 | 不进入标注/Embedding |
| `needs_review` | 不确定，需要人工复核 | 已填充 | > 0 | 人工复核后重新判定，**不能直接进入标注/Embedding** |

> 本版本**不再按字数**区分 `kept` / `kept`。只要 Segment 清洗后具有独立语义价值且与游戏研究相关，统一标记为 `kept`。

### 4.4 判定规则总览

```
对于每个 Segment：

1. 确定性噪声？ → removed_noise
2. 纯流程对话？ → removed_flow
3. 与游戏研究无关？ → removed_irrelevant
4. 包含研究相关信息？ → kept
5. 无法确定？ → needs_review
```

判定顺序**不可颠倒**。只有在前三类规则均不匹配时，才评估是否为有效内容或需要复核。

### 4.5 确定性噪声判定

#### 4.5.1 噪声定义

噪声是指**不具有独立语义价值的填充词或单字确认**。这类片段离开对话上下文后完全无意义，无法用于 AI 虚拟用户回答或画像聚类。

**关键约束**：噪声判定必须是**整段匹配**，不能部分匹配。因为包含"我觉得"而删除整段是错误的。

#### 4.5.2 中文噪声模式

| 类别 | 模式 | 示例 |
|------|------|------|
| 确认/附和 | 纯确认词组合，1-3 字短句 | "对。"、"嗯嗯。"、"好的好的。"、"可以。" |
| 否定 | 纯否定词组合 | "没有。"、"不知道。"、"不行。" |
| 语气词 | 单字感叹 | "啊。"、"哦。"、"呃。" |

**正则表达式**（整段完全匹配）：

```
^[对是嗯好行可可以]+[，,。.]?$|
^[没不][有会是知道清楚懂行能]+[，,。.]?$|
^[啊哦嗯呃唉哎哟嘿]$
```

#### 4.5.3 英文噪声模式

| 类别 | 示例 |
|------|------|
| 单字确认 | "Yeah.", "Yep.", "Nope.", "Yes.", "No.", "Okay.", "Ok.", "Sure.", "Right." |
| 感叹/评价 | "Cool.", "Great.", "Nice.", "Perfect.", "Fine.", "Alright.", "Absolutely.", "Exactly." |
| 社交/礼貌 | "Thanks.", "Sorry.", "Hello.", "Hi.", "Hey." |
| 含糊应答 | "Mmm.", "Mhmm." |

**正则表达式**（不区分大小写）：

```
^(Cool|Yeah|Yep|Nope|Yes|No|Okay|Ok|Sure|Right|Gotcha|Perfect|Fantastic|Great|Nice|Thanks|Sorry|Fine|Alright|Absolutely|Exactly|Definitely|Totally|Indeed|Correct|Fair|True|Maybe|Perhaps|Probably|Hello|Hi|Hey|Wow|What|Why|When|Where|How|Who)$|
^[Mm]+[hm]+[，,。.]?$
```

#### 4.5.4 噪声判定示例

```
✅ removed_noise：
"嗯。"           → 纯中文噪声，整段匹配
"对。"           → 纯中文噪声
"Yeah"           → 纯英文噪声
"Sure."          → 纯英文噪声
"Mhmm"           → 纯英文噪声

❌ 不是噪声（标记为 kept）：
"对，我觉得这个游戏手感很好。"     → 以"对"开头但有实质内容，不整段匹配
"Yeah I really like this game."  → 以"Yeah"开头但有实质内容
"Cool, the game is great."       → 同上
"我喜欢枪感。"                   → 包含游戏体验/偏好，是有效数据
"因为枪感好。"                   → 包含原因/动机，是有效数据
"玩APEX。"                       → 包含游戏行为，是有效数据
```

### 4.6 流程对话判定

#### 4.6.1 定义

流程对话是指**纯对话组织/管理性质的内容**，不包含任何游戏相关讨论。这些内容通常出现在访谈的开场、转场或结尾。

#### 4.6.2 英文流程对话模式

| 类别 | 示例 |
|------|------|
| 开场/转场 | "I'll start.", "Go ahead.", "Dial-up." |
| 礼貌/道歉 | "Sorry.", "Excuse me.", "Thank you." |
| 寒暄/附和 | "You look great.", "That's funny.", "That's great.", "Oh, cool." |
| 结束语 | "There you go.", "That's it.", "No sleep.", "All right." |

**正则表达式**（不区分大小写）：

```
^(I'll start\.?|Go ahead\.?|Dial-up\.?|Sorry\.?|Excuse me\.?|
You look great.*|That's funny\.?|That's great\.?|Oh, cool\.?|
Oh, yeah\.?|Yeah, yeah\.?|No, no\.?|
There you go\.?|That's it\.?|No sleep\.?|All right\.?|
Is it the new DLC\?|Happy early birthday\.?|Thank you\.?|
Probably not\.?|Cool\. All right\.?)$
```

#### 4.6.3 判定示例

```
✅ removed_flow：
"I'll start."       → 访谈开场，无游戏内容
"Go ahead."          → 让渡发言，无游戏内容
"Thank you."         → 礼貌用语，无游戏内容

❌ 不是流程对话（标记为 kept）：
"I really enjoy playing this game, it's great."  → 包含游戏评价
"Thank you, the game is fantastic."              → 以"Thank you"开头但有实质游戏内容
```

### 4.7 游戏相关性过滤

#### 4.7.1 目标

在去除噪声和流程对话后，进一步删除**与游戏行为、体验、偏好、动机、决策及其上下文无关**的 Segment。本规则不依赖字数，而依赖语义相关性。

#### 4.7.2 必须删除的内容

满足以下任一条件，标记为 `removed_irrelevant`：

| 类别 | 说明 | 示例 |
|------|------|------|
| 生活琐事 | 与游戏无关的个人日常 | "我昨天去吃饭了。"、"今天天气不错。" |
| 工作/学习细节 | 不关联游戏的具体工作/学习内容 | "我最近在赶一个项目。"、"期末考试很忙。" |
| 社交寒暄 | 与游戏无关的人际交流 | "你最近怎么样？"、"好久不见。" |
| 重复无信息附和 | 虽有实质词但无游戏相关内容 | "确实是这样。"、"我同意你的看法。" |
| 明显跑题 | 主持人引导下仍未回到游戏主题 | "我特别喜欢打篮球。"（无后续游戏关联） |

#### 4.7.3 必须保留的内容

以下信息即使简短也与游戏研究直接相关，不得删除：

| 类别 | 示例 |
|------|------|
| 游戏行为 | "我玩守望先锋。"、"最近在打Apex。" |
| 游戏体验 | "枪感很好。"、"画面不错。" |
| 游戏偏好 | "我喜欢辅助位。"、"偏好射击游戏。" |
| 游戏动机 | "因为朋友玩所以玩。"、"为了上分。" |
| 游戏决策 | "我选了黑豹。"、"决定不充钱。" |
| 游戏相关上下文 | "从穿越火线开始接触射击游戏。"、"小时候在网吧玩CS。" |

#### 4.7.4 判定方法

采用**关键词 + 语义规则**两级判定：

1. **关键词命中**：Segment 清洗后文本包含附录 A 游戏名、附录 B 游戏类型/术语、或通用游戏相关词（游戏、玩、枪、英雄、技能、段位、队友、匹配等），直接保留。
2. **语义规则**：未命中关键词但可能隐含游戏相关的，结合 `preceding_question` 判断：
   - 若 `preceding_question` 明确关于游戏，且回答是对该问题的直接应答（即使简短），保留。
   - 若 `preceding_question` 关于游戏，但回答完全跑题到生活/工作/学习且未拉回，删除。
   - 若 `preceding_question` 本身也与游戏无关（如纯寒暄），且回答无游戏内容，删除。

#### 4.7.5 示例

```
✅ removed_irrelevant：
"我最近在准备考试。" → 与游戏无关
"昨天和朋友出去吃饭了。" → 与游戏无关
"我觉得你说的对。" → 无游戏信息

✅ kept：
"我喜欢玩辅助。" → 游戏偏好
"因为枪感好。" → 游戏体验/动机
"从CS1.5开始玩射击游戏。" → 游戏经历
"我选黑豹配合队友浩克。" → 游戏行为
```

### 4.8 needs_review 判定条件

`needs_review` 的进入条件必须明确，不允许模型为了提高有效保留率而强行判 `kept`。

**进入 `needs_review` 的条件**（满足任一即进入）：

1. **仅凭 `preceding_question` 才能理解，且脱离上下文无法判断**：文本本身不包含足够的游戏/研究相关信息，但其 `preceding_question` 暗示可能是游戏相关回答
2. **模型无法确认是否具有独立语义价值**：文本可能存在歧义，模型无法确定它是否承载了用户的行为、体验、偏好、动机或决策信息
3. **文本包含游戏相关词汇但语义不完整**：例如"就是那个…"、"感觉跟…差不多"

**不允许进入 `needs_review` 的情况**：

- 已经明确判定为噪声、流程对话或无关内容的（直接 `removed_*`）
- 明确包含游戏相关信息的（直接 `kept`）
- 文本完全不含任何游戏/研究相关词汇且无上下文依赖的（可能是噪声或无关内容，走对应判定）

**示例**：

```
✅ needs_review：
preceding_question: "你觉得这个游戏的匹配机制怎么样？"
original_text: "还行吧。"
→ 脱离上下文无法判断"还行吧"指什么，需要人工确认

preceding_question: "你平时玩什么游戏？"
original_text: "就是那个。"
→ 语义不完整，无法判定

❌ 不应进入 needs_review（直接判定）：
"我喜欢无畏契约。" → 明确游戏内容 → kept
"嗯。" → 明确噪声 → removed_noise
"I'll start." → 明确流程 → removed_flow
"我最近在准备考试。" → 明确无关 → removed_irrelevant
```

### 4.9 判定优先级

当一段文本同时匹配多个规则时：

```
确定性噪声 > 纯流程对话 > 游戏无关内容 > 有效内容 > needs_review
```

即：先判定是否噪声，再判定是否流程对话，再判定是否与游戏无关，然后判定是否为有效内容，最后才进入 `needs_review`。

## 5. Segment 文本轻度标准化

### 5.1 适用范围

仅对 `cleaning_status = "kept"` 或 `"needs_review"` 的 Segment 执行。

同时，`preceding_question` 也参与轻度标准化与中文化（见 §4.2），用于文件输出。

### 5.2 标准化规则

| 步骤 | 操作 | 示例 |
|:---:|------|------|
| 1 | 去除首尾空白 | `"  游戏很好玩  "` → `"游戏很好玩"` |
| 2 | 合并多余空格（2 个以上空格合并为 1 个） | `"hello   world"` → `"hello world"` |
| 3 | 合并连续标点（中英文） | `"很好，，不错"` → `"很好，不错"`；`"Great.."` → `"Great."` |
| 4 | 去除开头无意义填充词 | 见 §5.3 |

### 5.3 可删除的开头填充词

**仅删除开头位置的、不改变句子语义的无意义填充词**：

| 可删除 | 条件 |
|------|------|
| 那个 | 仅在开头，且删除后不改变句子含义 |
| 怎么说呢 | 仅在开头 |
| 嗯/啊/哦 | 仅在开头，且独立于句子内容 |

**正则表达式**：`^[那个怎么说呢嗯啊哦]+[，,。.]?\s*`

**不可删除的填充词**（即使出现在开头）：

| 词 | 原因 |
|------|------|
| 就是 | 可能表示解释/强调 |
| 然后 | 可能表示时间顺序 |
| 但是/不过 | 表示转折 |
| 其实 | 表示强调/对比 |
| 因为/所以 | 表示因果 |
| 而且 | 表示递进 |
| 感觉/觉得 | 表示主观判断 |
| 可能/应该/大概 | 表示不确定性 |
| 确实/当然 | 表示确认/强调 |

### 5.4 标准化前后对比

```
✅ 正确标准化：
输入："  那个我觉得这个游戏吧，手感真的  很好，画面也  不错。  "
输出："我觉得这个游戏吧，手感真的 很好，画面也 不错。"

输入："怎么说呢，就是感觉  APEX  的枪感特别  好  "
输出："就是感觉 APEX 的枪感特别 好"
（保留了"就是"和"感觉"——它们承载语义）

❌ 错误标准化（过度清洗）：
输入："因为枪感好，所以我一直玩。"
错误输出："枪感好，我一直玩。"
→ 丢失了因果关系，对后续动机识别有严重影响

输入："我感觉这个游戏比较适合我。"
错误输出："这个游戏比较适合我。"
→ 丢失了主观判断的不确定性
```

### 5.5 char_count 计算

`char_count` = `cleaned_text` 的字符数（去除首尾空白后的长度）。

对于 `removed_*` 的 Segment，`char_count` = 0。

## 6. Segment 中文化

### 6.1 适用范围

仅对 `cleaning_status = "kept"`（含临时标记，后续将细分为 kept）或 `"needs_review"` 的 Segment 执行。

### 6.2 中文化原则

> **轻度翻译 + 轻度口语整理，不是语义重写。保留语义强度，禁止弱化程度/态度/不确定性。**

目标：让英文原文在 `cleaned_text` 中以中文形式呈现，保持口语感和原始表达风格。

**语义强度保留规则**：

| 英文 | 禁止的错误翻译 | 正确翻译 |
|------|------|------|
| way more / much more | 就是竞技性强 | 竞技性强很多 |
| really like | 喜欢 | 很喜欢 |
| kind of / sort of | （删除） | 有点 / 算是 |
| I think / I feel | （删除，变事实陈述） | 我觉得 / 我感觉 |
| you know? | （删除） | 你知道吗 / 你懂吧 |
| I mean / like | （删除所有口语缓冲） | 就是 / 怎么说呢（保留口语感） |
| maybe / probably | （删除） | 可能 / 大概 |
| just | （删除） | 就是 / 就 |

**核心原则**：可以删除纯口语噪声（如 "um", "uh"），但**不能删除表示程度、态度、不确定性的修饰词**。

### 6.3 中文化示例

```
原文："I really like Apex because the gunplay feels great."

✅ 正确中文化：
"我很喜欢Apex英雄，因为枪感很好。"
（保留了"很"的程度修饰）

❌ 错误中文化（过度书面化）：
"我非常喜欢Apex英雄，因为该游戏的枪械操作手感极佳。"
→ 过度书面化，丢失口语感
```

```
原文："Yeah I mean like, Valorant is just way more competitive you know?"

✅ 正确中文化：
"我觉得无畏契约的竞技性强很多，你懂吧。"
（保留了"我觉得"的态度标记、"强很多"的程度、"你懂吧"的口语确认）

❌ 错误中文化（丢失语义强度）：
"无畏契约就是竞技性强很多。"
→ 丢失了"我觉得"（主观判断）、"way more"被弱化为"强很多"（"way"的程度丢失不够明显）

❌ 更差的中文化：
"无畏契约竞技性更强。"
→ 丢失了所有主观态度、程度修饰和口语特征
```

### 6.4 中文原文的处理

中文原文的 Segment 不需要翻译，但需要经过 §5 的轻度标准化。`cleaned_text` 与 `original_text` 的差异仅来自标准化（去首尾空格、合并空格、去开头填充词），不应有语义变化。

### 6.5 游戏名中文化

`cleaned_text` 中的游戏名统一使用中文标准名（附录 A）。

```
原文："I play Valorant and Apex."
cleaned_text："我玩无畏契约和Apex英雄。"
```

## 7. Segment 去重

### 7.1 去重策略

**仅识别近乎逐字复制的重复，不做激进语义去重。**

去重不物理删除 Segment，而是将重复的 Segment 标记为 `removed_duplicate`。

### 7.2 去重规则

#### 7.2.1 第一层：完全重复

`cleaned_text` 完全相同 + 同一 `speaker_id` + 同一 `preceding_question`。

→ 保留一条，其余标记 `removed_duplicate`。

#### 7.2.2 第二层：近乎逐字复制

满足以下**全部条件**才判定为重复：

1. 同一 `speaker_id` + 同一 `preceding_question`
2. 两条 `cleaned_text` 的 trigram Jaccard 相似度 > 0.9
3. **两条文本都不是对方的信息超集**（即一条不是另一条加上新增信息）
4. 两条文本的 `cleaned_text` 字符数均 ≥ 15（短文本不做 trigram 去重）

→ 保留字符数最长的一条，其余标记 `removed_duplicate`。

#### 7.2.3 信息超集保护

**如果一条文本包含另一条文本的全部信息，并增加了新信息，两条都保留。**

```
示例：
A: "我喜欢Apex英雄，因为枪感很好。"
B: "我喜欢Apex英雄，因为枪感很好，但是匹配很差。"
→ B 是 A 的信息超集（包含了 A 的全部 + 新增信息）
→ 两条都保留，不标记为重复
```

```
示例：
A: "我喜欢这个游戏，因为枪感很好。"
B: "我喜欢这个游戏，因为枪感非常好。"
→ A 和 B 不是信息超集关系（"很好" vs "非常好"是程度差异，不是新增信息）
→ 如果 trigram > 0.9，视为近乎逐字复制，保留一条
```

#### 7.2.4 短文本豁免

`cleaned_text` 字符数 < 15 的 Segment 不做 trigram 去重。短文本的高相似度不一定是重复，可能是不同人对同一问题的简短回答，这是有效数据。

### 7.3 分组规则

| 分组键 | 说明 |
|------|------|
| `speaker_id` | 同一说话人 |
| `preceding_question` | 同一提问语境 |

不同说话人的相同文本不去重（可能是不同人对同一问题的相同回答，是有效数据）。
不同提问下的相同文本不去重（语境不同，含义可能不同）。

### 7.4 去重执行字段

去重在 `cleaned_text` 上执行（标准化 + 中文化之后），确保同一内容的不同表达形式能被识别。

`original_text` 作为最终追溯依据，不参与去重计算。

### 7.5 不在清洗阶段处理的重复

以下情况**不在清洗阶段去重**，留给后续 Embedding 向量相似度检测：

```
A: "我喜欢Apex英雄，因为枪感很好。"
B: "我比较喜欢Apex英雄，主要就是枪感比较好。"
→ 语义高度相似但 trigram 相似度可能不高
→ 不在清洗阶段处理
```

### 7.6 去重后处理

去重后，被标记为 `removed_duplicate` 的 Segment：
- `cleaned_text` = null
- `char_count` = 0
- 保留 `original_text` 不变
- 不进入标注/Embedding

## 8. 自我介绍数据提取与合并

> **概念说明**：§8 属于**结构化档案提取**（Extraction / Structuring），不属于 Segment Cleaning 本身。仅因其输入依赖清洗后的 Segment，故在本 Pipeline 中编排执行。这不与 §1.4「清洗阶段不做 Fact 提取」产生概念冲突 — Profile 和 Gaming Background 是参与者属性，不是 Fact。

### 8.1 设计目标

提取阶段产出的 `respondents` 表包含从外部数据（问卷、报名表）获取的参与者背景信息。**在实际数据中，提取阶段产出的 `respondents` 大部分字段为空值**（`""`、`null`、`[]`），例如：

```json
{
  "speaker_id": "P001",
  "profile": {
    "name": "",
    "age": null,
    "gender": "",
    "occupation": "",
    "education": ""
  },
  "gaming_background": {
    "current_games": [],
    "platform": [],
    "experience_years": null,
    "genre_experience": []
  }
}
```

因此，清洗阶段**必须**从自我介绍 Segment 中提取档案和游戏背景信息，实际填充 `respondents` 表。这是清洗阶段的核心任务之一，不是可选的补充操作。

> **核心原则（§1.6 P4）**：自我介绍中同时包含档案信息、游戏背景、体验/偏好。档案和游戏背景归入 `respondents`，体验/偏好保留在 Segment 中，不进入档案。

### 8.2 识别自我介绍 Segment

自我介绍 Segment 通过以下特征综合判定，**优先级递减**：

| 优先级 | 识别维度 | 判定规则 | 示例 |
|:---:|------|------|------|
| **1（强信号）** | `preceding_question` 包含自我介绍关键词 | 包含"介绍""游戏经历""背景""玩过哪些""introduce""background""gaming experience""tell me about"等 | "大家介绍一下自己的游戏经历…" |
| **2（强信号）** | `original_text` 包含明确自我介绍内容 | 包含年龄、职业、游戏列表、游戏时长等信息 | "我今年27岁，是工程师，主要玩无畏契约和使命召唤" |
| **3（辅助信号）** | Segment 位置靠前 | 同一 `speaker_id` 在一个 `source_file` 内的前几个 Segment | 访谈通常以自我介绍开头 |

**识别流程**：

```
1. 遍历所有 cleaning_status = "kept" 的 Segment
2. 对每个 Segment：
   a. preceding_question 包含自我介绍关键词？ → 强信号
   b. original_text 包含档案/游戏背景信息？ → 强信号
   c. segment_index 靠前？ → 辅助信号
3. 判定：
   - 满足 a + b → 确认为自我介绍 Segment
   - 满足 b（但 a 不满足）→ 检查 c，若靠前 → 可能是自我介绍
   - 仅满足 a（但 b 不满足）→ 可能是对自我介绍问题的简短回答，根据内容判定
   - 仅满足 c → 不判定为自我介绍
```

> **注意**：不要把"前 3 个 Segment"作为硬性条件。自我介绍的判定以 `preceding_question` 和内容特征为主要依据，位置仅作为辅助参考。座谈会中自我介绍可能出现在 segment_index = 5/6/7。

### 8.3 提取档案信息（Profile）

从自我介绍 Segment 的 `original_text` 中提取以下字段，写入 `respondents.profile`（jsonb）：

| 字段 | 提取来源 | 示例 |
|------|------|------|
| `name` | "我叫/我是/My name is/I'm {name}" | "张伟" |
| `age` | "我今年{数字}岁/I'm {数字} years old" | 28 |
| `gender` | "男/女/男性/女性/male/female" | "男" |
| `occupation` | "我是{职业}/I'm a {occupation}/I work as" | "工程师" |
| `education` | "本科/硕士/大专/college/bachelor/master" | "本科" |
| `location` | "在{城市}/住在{城市}/from {city}/live in" | "深圳" |
| `self_intro_raw` | 自我介绍 Segment 的完整 `original_text`（**原语言，不翻译**） | 原始自我介绍全文 |

**提取规则**：

| 规则 | 说明 |
|------|------|
| **不强制全部提取** | 自我介绍中没提到的字段保持为空，不推断 |
| **空值直接写入** | 提取阶段产出的字段值为 `null`、`""`（空字符串）或 `[]`（空数组）时，视为"无数据"，直接写入提取值，不视为冲突 |
| **非空值冲突时保留多源** | 若提取阶段已有非空值（如外部问卷已填写年龄），且与自我介绍提取值不同，按 §8.6 冲突数据结构处理 |
| **保留原文** | 所有提取结果附带 `source_segment_index`，可追溯到原始 Segment |
| **raw 字段保持原语言** | `self_intro_raw` 不翻译，保持原语言 |

### 8.4 提取游戏背景（Gaming Background）

从自我介绍 Segment 的 `original_text` 中提取以下字段，写入 `respondents.gaming_background`（jsonb）：

| 字段 | 提取来源 | 示例 |
|------|------|------|
| `current_games` | 游戏名列表，**统一用中文标准名**（附录 A） | `["无畏契约", "Apex英雄"]` |
| `platform` | "PC/手机/主机/PS5/Xbox/Switch/console/mobile" | `["PC"]` |
| `experience_years` | "玩了{数字}年/been playing for {数字} years" | 5 |
| `daily_play_hours` | "每天{数字}小时/{数字} hours a day/every day" | 2 |
| `weekly_play_hours` | "每周{数字}小时/{数字} hours a week/per week" | 15 |
| `genre_experience` | 品类名称（FPS/MOBA/大逃杀/搜打撤/MMO…） | `["FPS", "战术竞技"]` |
| `gaming_self_intro_raw` | 自我介绍 Segment 中与游戏相关的原文部分（**原语言，不翻译**） | 游戏经历原文摘录 |

**提取规则**：

| 规则 | 说明 |
|------|------|
| **游戏名用中文标准名** | 匹配到的游戏名按附录 A 统一为中文标准名（无畏契约，不是 Valorant） |
| **去重** | 同一游戏名只保留一个（如"瓦"和"Valorant"都匹配到，只保留"无畏契约"） |
| **空值直接写入** | 提取阶段产出的字段值为 `null`、`""` 或 `[]` 时，直接写入提取值。例如 `current_games: []` → 写入 `["无畏契约", "Apex英雄"]` |
| **非空值冲突时保留多源** | 若提取阶段已有非空值，且与自我介绍提取值不同，按 §8.6 冲突数据结构处理 |
| **品类经验不推断** | 只说"我玩了很多射击游戏"不标"FPS品类经验"，必须原文明确提到品类名称 |
| **raw 字段保持原语言** | `gaming_self_intro_raw` 不翻译 |

### 8.5 不进入档案的内容

以下内容虽然出现在自我介绍中，但**不提取到 Profile 或 Gaming Background**，保留在 Segment 中：

```
"我觉得无畏契约枪感特别好。"
"跟朋友一起玩比较开心。"
"最近不太想打排位了。"
"这个游戏匹配机制太差了。"
```

这些是**体验/偏好/态度/情绪**，属于 Segment 层，后续进入标注。

### 8.6 与已有档案合并（冲突处理）

#### 8.6.1 合并流程

```
1. 读取 respondents 表中该 (source_file, speaker_id) 的现有记录
2. 从自我介绍 Segment 提取 profile 和 gaming_background 数据
3. 字段级合并，按以下规则逐字段判断：
   a. 目标字段为空值（null / "" / []）→ 直接写入提取值，source = "self_intro"
      - 这是最常见的情况：提取阶段产出的 respondents 大部分字段为空
   b. 目标字段已有非空值 → 比较是否相同
      - 相同 → 跳过
      - 不同 → 保留多源，不覆盖（见 §8.6.2）
4. 更新 respondents 表
```

**空值判定标准**：

| 值 | 判定 | 处理 |
|------|:---:|------|
| `null` | 空值 | 直接写入提取值 |
| `""`（空字符串） | 空值 | 直接写入提取值 |
| `[]`（空数组） | 空值 | 直接写入提取值 |
| `"张伟"`（非空字符串） | 有值 | 进入冲突判定 |
| `28`（非 null 数字） | 有值 | 进入冲突判定 |
| `["无畏契约"]`（非空数组） | 有值 | 进入冲突判定 |

#### 8.6.2 冲突数据结构

**清洗模型不自行决定哪个值是"真值"。**

当提取值与已有值冲突时，使用以下数据结构保留多源信息：

```json
{
  "age": {
    "value": 27,
    "source": "self_intro",
    "conflict": true,
    "conflict_values": [
      {
        "value": 25,
        "source": "external"
      }
    ]
  }
}
```

**字段说明**：

| 字段 | 含义 |
|------|------|
| `value` | 当前使用的值（优先取自我介绍中的值，因为通常更准确） |
| `source` | 值的来源：`"external"`（外部问卷/报名表）或 `"self_intro"`（自我介绍提取） |
| `conflict` | 是否存在冲突。`true` = 不同来源给出了不同值 |
| `conflict_values` | 所有冲突版本的列表，每项包含 `value` 和 `source` |

**选择规则**：
- `value` 默认取 `self_intro` 来源的值（访谈中用户自述通常比外部问卷更准确）
- 但下游使用时应检查 `conflict` 字段，根据业务需求决定使用哪个值
- 对于简单字段（如 `name`、`gender`），如果只有一个来源，直接使用简单值而非嵌套结构：

```json
// 无冲突时 → 简单值
{ "name": "张伟" }

// 有冲突时 → 嵌套结构
{ "age": { "value": 27, "source": "self_intro", "conflict": true, "conflict_values": [...] } }
```

### 8.7 提取示例

**输入** — 自我介绍 Segment：

```json
{
  "source_file": "Deadlock竞品研究/座谈会笔录-G1.docx",
  "segment_index": 3,
  "speaker_id": "G1-HJX",
  "preceding_question": "大家介绍一下自己的游戏经历...重点讲一下MOBA类和射击类",
  "original_text": "MOBA类主要就是英雄联盟，然后射击类游戏就是守望先锋、无畏契约、APEX。",
  "cleaned_text": "MOBA类主要就是英雄联盟，然后射击类游戏就是守望先锋、无畏契约、Apex英雄。"
}
```

**提取结果**：

```
┌── Profile
│   (本段未包含年龄、职业等，不提取)
│
├── Gaming Background
│   current_games: ["英雄联盟", "守望先锋", "无畏契约", "Apex英雄"]
│   genre_experience: ["MOBA", "FPS"]
│
└── 合并到 respondents
    speaker_id = "G1-HJX" 的 gaming_background.current_games
    如果已有值 ["死锁"]，合并后为 ["死锁", "英雄联盟", "守望先锋", "无畏契约", "Apex英雄"]
```

**输入** — 包含档案和游戏偏好的自我介绍：

```
"我叫张伟，今年28岁，主要玩无畏契约和Apex英雄，平时每天玩两个小时，
我觉得无畏契约枪感特别好。"
```

**提取结果**：

```
┌── Profile
│   name: "张伟"
│   age: 28
│
├── Gaming Background
│   current_games: ["无畏契约", "Apex英雄"]
│   daily_play_hours: 2
│
└── 不提取到档案（保留在 Segment 中）
    "我觉得无畏契约枪感特别好。" → 体验/偏好，留在 Segment
```

### 8.8 边界情况

| 情况 | 处理方式 |
|------|------|
| 同一参与者有多段自我介绍 | 全部提取，合并时去重 |
| 自我介绍中无任何档案信息 | 不提取，`respondents` 保持原样 |
| 提取值与已有值冲突 | 按 §8.6.2 冲突数据结构保留多源 |
| 游戏名无法匹配附录 A | 原样保留在 `current_games` 中，标记 `unmatched: true` |
| 英文自我介绍中夹杂中文游戏名 | 先按语言判定分流，再按对应规则提取 |
| 参与者没有自我介绍 Segment | 跳过，`respondents` 保持提取阶段的值 |

## 9. 参与者档案清洗

### 9.1 输入格式

参与者档案的输入来自提取阶段产出的 `respondents` 表，以及 §8 自我介绍提取后合并的数据：

```json
{
  "source_file": "研究项目/座谈会文件名.docx",
  "speaker_id": "P001",
  "display_name": null,
  "group_code": "G1",
  "profile": {
    "name": "张伟",
    "age": 28,
    "occupation": "工程师",
    "location": "深圳"
  },
  "gaming_background": {
    "current_games": ["无畏契约", "Apex英雄"],
    "platform": ["PC"],
    "experience_years": 5,
    "genre_experience": ["FPS"]
  },
  "background": {}
}
```

### 9.2 清洗范围

| 字段 | 是否清洗 | 清洗方式 |
|------|:---:|------|
| `profile` 内的文本字段 | ✅ 是 | 中文化 + 轻度文本清理 |
| `gaming_background` 内的游戏名 | ✅ 是 | 统一为中文标准名（附录 A） |
| `background` 原始文本 | ✅ 是 | 中文化 + 轻度文本清理 |
| `self_intro_raw` | ❌ 否 | 保持原语言原文 |
| `gaming_self_intro_raw` | ❌ 否 | 保持原语言原文 |
| `source_file` | ❌ 否 | 保持不变 |
| `speaker_id` | ❌ 否 | 保持不变 |
| `group_code` | ❌ 否 | 原样保留（含不确定标记如 `G3?`） |

### 9.3 轻度文本清理规则

档案清洗的目标是**轻量整理**，不是**重写**。只删除真正无语义贡献的内容。

#### 9.3.1 可删除的内容

| 内容 | 条件 | 示例 |
|------|------|------|
| 【画像】前缀 | 开头 | `"【画像】大家好…"` → `"大家好…"` |
| 自我介绍套话 | 开头，且独立于实质内容 | `"大家好，我叫张伟。"` → 仅删除"大家好，" |
| 句末单字语气词 | 独立于句子内容 | `"玩无畏契约啊。"` → `"玩无畏契约。"` |
| 括号注释 | 全段 | `"（当时细糠）"` → 删除 |

#### 9.3.2 不可删除的内容

以下内容**绝对不能删除**，因为它们承载语义信息：

| 内容 | 原因 |
|------|------|
| 因为/所以 | 因果关系 |
| 但是/不过 | 转折关系 |
| 而且 | 递进关系 |
| 感觉/觉得 | 主观判断，降低断言强度 |
| 可能/应该/大概 | 不确定性 |
| 其实/确实/当然 | 强调/确认 |
| 就是 | 解释/强调 |
| 然后 | 时间顺序/因果弱化 |

#### 9.3.3 清洗示例

```
✅ 正确清洗：
输入："【画像】那个大家好，我叫张伟，我今年28岁，我的兴趣就是打游戏。
然后我主要玩无畏契约跟Apex英雄，怎么说呢，就是感觉这两个游戏枪感特别好啊。"

输出："我叫张伟，今年28岁，兴趣就是打游戏。然后主要玩无畏契约和Apex英雄，就是感觉这两个游戏枪感特别好。"

保留了："然后"（时间顺序）、"就是"（强调）、"感觉"（主观判断）

❌ 错误清洗：
"我叫张伟，打游戏。主要玩无畏契约、Apex英雄，这两个游戏枪感特别好。"
→ 丢失了"然后"（顺序）、"就是"（强调）、"感觉"（主观判断）
```

### 9.3.4 字段级合理性校验

档案清洗除文本清理外，须对上游提取阶段可能产生的明显错误字段进行校验。**仅清空明显不合理的值，不推测、不补全。**

#### 9.3.4.1 occupation 校验

`profile.occupation` 出现以下任一情况时视为提取错误，清空为 `null`：

| 情况 | 示例 | 说明 |
|------|------|------|
| 与身份标识相同 | `"G1-ZHS"`、`"志城"` | 等于 `speaker_id`、`display_name` 或 `profile.name` |
| 匹配 ID 模式 | `"P001"`、`"G1-LJH"` | 形如 `P`/`G` + 数字，或仅由 2–6 位字母数字组成 |
| 含游戏时间状语 | `"初中开始接触"` | 含"开始"、"接触"、"玩"等词 |

#### 9.3.4.2 education 校验

`profile.education` 出现以下任一情况时视为提取错误，清空为 `null`：

| 情况 | 示例 | 说明 |
|------|------|------|
| 低学历且非明确未成年 | `"小学"` 且 `age` 为空或 `age >= 18`；`"初中"` 且 `age` 为空或 `age >= 18` | `"小学"`/`"初中"`在成人座谈会中多为"小学/初中时候"的时间状语误识别；只有 `age < 18` 时才保留 |
| 含游戏上下文 | `"初中开始接触"` | 含"开始"、"接触"、"玩"等词 |

#### 9.3.4.3 校验原则

- 仅删除，不补全：不能根据推测把 `occupation` 改为"学生"。
- 模糊值保留：如 `"上班族"`、`"自由职业"` 等不在黑名单的值保留，交给下游人工复核。
- 本规则只覆盖明显机器误识别，不建立完整职业/学历白名单。

### 9.4 中英文判定

#### 9.4.1 三分类

```python
def classify_language(text: str) -> str:
    """判定文本语言：'zh' | 'en' | 'mixed'"""
    chinese_chars = sum(1 for c in text if '一' <= c <= '鿿')
    english_chars = sum(1 for c in text if c.isalpha() and ord(c) < 128)
    total = max(chinese_chars + english_chars, 1)

    if chinese_chars / total > 0.5:
        return "zh"
    elif english_chars / total > 0.5:
        return "en"
    else:
        return "mixed"
```

#### 9.4.2 分流规则

| 判定结果 | 处理方式 |
|:---:|------|
| `zh` | 按中文清洗规则 |
| `en` | 先中文化，再按中文清洗规则 |
| `mixed` | 保留混合状态，按中文清洗规则处理中文部分，英文部分轻量翻译 |

**示例**：

```
"I like APEX，主要是因为枪感很好。"
→ 中文占比 > 英文占比 → "zh"
→ 按中文清洗，英文部分轻量翻译

"I like APEX because the gunplay feels great."
→ 英文占比 > 中文占比 → "en"
→ 先中文化，再清洗
```

### 9.5 游戏名标准化

档案中的游戏名统一使用中文标准名（附录 A）。

```
清洗前：current_games: ["Valorant", "COD", "APEX"]
清洗后：current_games: ["无畏契约", "使命召唤", "Apex英雄"]
```

## 10. 清洗输出格式

### 10.1 输出总览

清洗完成后，生成**单一清洗结果文件**，作为下游标注与 Embedding 的唯一消费接口。

```text
<输出根目录>/
└── <source_file>_cleaned.json          # 清洗结果文件
```

**设计原则**：

| 原则 | 说明 |
|------|------|
| **单一文件** | 每个源文件只生成一个 JSON，不再区分 cleaned/ 与 review/ 目录 |
| **respondents 在前** | 文件顶部先输出清洗后的 respondents，再输出 segments |
| **不保留原始语句** | 文件输出中不包含 `original_text`，问题和回答均为清洗后的中文 |
| **仅保留有效与待复核内容** | 输出包含 `kept` 与 `needs_review`；`removed_*` 不输出 |
| **按语义过滤，不按字数** | 不再区分 `kept` / `kept_short`，有效内容统一标记为 `kept` |

**文件命名规则**：

- 将 `source_file` 中的路径分隔符 `/` 和 `\` 替换为 `_`，后缀替换为 `_cleaned.json`
  - 示例：`Deadlock竞品研究/座谈会笔录-G1.docx` → `Deadlock竞品研究_座谈会笔录-G1_cleaned.json`
- 若某源文件无 `kept` 且无 `needs_review` 内容，则不生成输出文件

## 11. 质量指标

### 11.1 清洗率目标

| 指标 | 目标值 | 说明 |
|------|:---:|------|
| 噪声率 | 5%–10% | `removed_noise` 占总片段的比例 |
| 流程对话率 | < 2% | `removed_flow` 占比 |
| 去重率 | 1%–3% | `removed_duplicate` 占比 |
| 短文本率 | 5%–8% | `kept` 占比（保留，仅统计） |
| 待复核率 | < 5% | `needs_review` 占比 |
| **有效保留率** | **≥ 80%** | `kept` 占比 |

### 11.2 清洗质量检查

| 检查项 | 标准 | 验证方式 |
|------|------|------|
| `original_text` 未被修改 | 清洗前后完全一致 | 全量 diff |
| 所有 Segment 仍在库中 | 清洗后的 Segment 数量 = 清洗前 | 全量计数 |
| `cleaning_status` 非空 | 所有 Segment 的 `cleaning_status` 有值 | 全量检查 |
| `kept` 的 `cleaned_text` 非空 | `kept`/`needs_review` 的 `cleaned_text` 不为 null | 全量检查 |
| `removed_*` 的 `cleaned_text` 为 null | 被标记为移除的片段 `cleaned_text` = null | 全量检查 |
| 游戏名已中文化 | `current_games` 中无英文游戏名（特殊情况标记 `unmatched`） | 随机抽样 10% |
| 因果/态度词未被删除 | `cleaned_text` 中保留了"因为""所以""感觉""觉得"等 | 随机抽样 10% |
| 短但有效的文本未被误删 | `kept` 中的文本确实包含游戏内容 | 随机抽样 20% |
| `self_intro_raw` 保持原语言 | raw 字段未被翻译 | 全量检查 |
| `preceding_question` 未进入 `cleaned_text` | `cleaned_text` 中不含 `preceding_question` 的内容 | 随机抽样 5% |
| **文件输出完整性** | 每个有 `kept` 或 `needs_review` 的源文件均生成 `_cleaned.json` | 全量计数 |
| **文件内容一致性** | 输出文件中的 Segment 在数据库中 `cleaning_status` 为 `kept` 或 `needs_review` | 全量交叉验证 |
| **无效内容未输出** | 输出文件中不含 `removed_*` 的 Segment | 全量检查 |
| **summary 一致性** | `summary` 中的统计数与数据库实际状态一致 | 全量交叉验证 |
| **文件输出 preceding_question 为中文** | 输出文件中英文源文件的 `preceding_question` 已翻译为中文 | 随机抽样 10% |
| **文件输出不含 original_text** | 输出文件中每条 Segment 不包含 `original_text` 字段 | 全量检查 |
| **respondents 在 segments 之前输出** | 输出文件顶层字段顺序为 `respondents` → `segments` | 全量检查 |

### 11.3 边界情况处理

| 情况 | 处理方式 |
|------|------|
| 片段只包含标点符号 | 标记 `removed_noise` |
| 片段包含大量空格但无实质内容 | 标准化后为空 → 标记 `removed_noise` |
| 中英混合噪声（如 "嗯 Yeah 对"） | 标记 `removed_noise` |
| 同一片段同时匹配噪声和流程模式 | 优先级：噪声 > 流程 |
| 同一说话人不同提问下几乎相同的回答 | 不跨组去重，保留（不同语境） |
| `preceding_question` 为 null 的片段 | 正常参与清洗，去重时 `null` 自成一个分组 |
| 清洗后 `cleaned_text` 与 `original_text` 完全相同 | 正常，`cleaning_status = "kept"` |
| 无法确定有效性的片段 | 标记 `needs_review`，不标记为 `removed_*` |
| 去重时一条是另一条的信息超集 | 两条都保留，不标记为重复 |

### 11.4 清洗幂等性

清洗操作必须是**幂等的**：对同一批数据执行两次清洗，结果应完全相同。

保证幂等的方式：
- 清洗前检查 `cleaning_status` 是否为 null，非 null 则跳过
- 所有规则均为确定性规则（无随机性）
- 去重排序在相同输入下结果一致
