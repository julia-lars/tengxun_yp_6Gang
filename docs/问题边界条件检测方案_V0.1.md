## 1. 问题定义

### 1.1 核心问题

当前系统（群体画像 / KOL 分身）在面对用户提问时，**缺乏统一的边界检测机制**。系统可能对以下类型的问题尝试生成回答：

| 问题类型 | 示例 | 风险 |
| --- | --- | --- |
| 明显领域外 | "今天天气怎么样？" | 低风险，容易识别 |
| 领域内但数据库未覆盖 | "CS2 玩家为什么喜欢 AWP？"（数据库只有使用率，无偏好原因） | **高风险** — 语义接近数据库内容，但实际超出证据能力 |
| 领域内但问题类型不支持 | "预测下个赛季 CS2 玩家数量"（数据库只有历史数据，无预测能力） | 中风险 |
| 领域内且有充分证据 | "CS2 玩家使用 AK 的比例是多少？" | 目标回答 |

**核心判断**：

> 这不是一个普通的"相关性分类"问题，而是一个**受限知识域下的 Open-Set Recognition + Knowledge Coverage Detection** 问题。系统需要判断的不是"问题是否相关"，而是"数据库是否具备回答该问题的能力"。

### 1.2 关键区分

```
射击游戏相关 ≠ 数据库可回答
```

系统必须能够区分：

- **Domain IN**（属于射击游戏领域）
- **Knowledge Coverage OUT**（数据库没有覆盖该知识）

这两者之间的差距是 Hard Negative 的主要来源，也是系统最危险的失败模式。

### 1.3 统一入口原则

```
                    Boundary Engine
                         │
                ┌────────┴────────┐
                │                 │
             群体画像            KOL 分身
                │                 │
             Response           Response
```

> **人格决定回答风格，不能决定知识边界。** 同一个问题，无论由 KOL A、KOL B 还是群体画像 C 回答，都必须先经过同一个 Boundary Engine 判定 IN/OUT，然后才允许不同 Persona 生成差异化回答。

## 2. 设计目标与约束

### 2.1 功能目标

| 编号 | 目标 | 说明 |
| --- | --- | --- |
| G1 | 统一边界检测 | 所有问答入口共用同一套 Boundary Engine |
| G2 | 低延迟 | 大部分问题通过规则/Embedding 直接判定，不经过 LLM |
| G3 | 低成本 | Canonicalization 不用 LLM；仅灰区问题调用 LLM Judge |
| G4 | 高一致性 | 相同 / 相似问题得到相同边界结果；关键语义变化时边界正确翻转 |
| G5 | 可校准 | 阈值通过 Benchmark 校准，不人工拍定 |
| G6 | 可演进 | 支持版本化：Boundary Version、Threshold Version、Embedding Model Version |

### 2.2 错误优先级（按优先级排序）

| 优先级 | 错误类型 | 含义 |
| --- | --- | --- |
| **① 最高** | False Accept (FA) | 实际 OUT，判为 IN → 系统对边界外内容生成回答 |
| **② 高** | Hard Negative FA | 语义接近数据库内容但实际 OUT，仍判为 IN — FA 中最危险的子类 |
| **③ 中** | False Reject (FR) | 实际 IN，判为 OUT → 系统拒答本可回答的问题 |

> 阈值选择不以最高 Accuracy 为目标，而是以**低 False Accept Rate（尤其是 Hard Negative 子集）**为首要约束。

### 2.3 性能目标

| 指标 | 目标 |
| --- | --- |
| LLM 调用比例 | 仅灰区问题调用 LLM Judge（目标：LLM 不出现在 Canonicalization 或快速路径中） |
| 单次判定延迟（非 LLM 路径） | < 50ms |
| 单次判定延迟（LLM 路径） | < 2s |

## 3. 核心概念：Answerability

### 3.1 定义

> **Answerability** = 数据库是否拥有足够证据，以支持该问题类型的可靠回答。

这不是"数据库有没有相关内容"（Semantic Match），而是"数据库能否回答这个问题"（Evidence-Backed Answerability）。

### 3.2 示例

数据库包含：

```
AK 使用率 = 43%
M4 使用率 = 37%
```

| 用户问题 | Semantic Match | Answerability | 判定 |
| --- | --- | --- | --- |
| "AK 使用率是多少？" | ✅ 高 | ✅ 有证据 | **IN** |
| "AK 和 M4 哪个使用率更高？" | ✅ 高 | ✅ 有证据（可比较） | **IN** |
| "AK 为什么比 M4 更受欢迎？" | ✅ 高 | ❌ 无证据（无偏好原因数据） | **OUT** |
| "下一版本 AK 会不会削弱？" | ✅ 中 | ❌ 无证据（无预测能力） | **OUT** |

### 3.3 判定模型

```
                    Question
                       │
              ┌────────┴────────┐
              │                 │
         Semantic Match      Evidence
         (像不像数据库知识)    (能不能回答)
              │                 │
              └────────┬────────┘
                       │
                 Answerability
                       │
                 IN / OUT
```

**Semantic Match** 由 Embedding 层判断（轻量、快速）。**Evidence** 由 LLM Judge 判断（仅在灰区触发，结构化判定）。**Hard Rules** 负责极明显的边界（快速过滤）。

## 4. 系统架构

### 4.1 总体判定流程

```
                    USER QUERY
                        │
                        ▼
              ┌──────────────────┐
              │ 1. Exact Query   │
              │    Cache         │──→ Hit ──→ 返回缓存结果
              └────────┬─────────┘
                       │ Miss
                       ▼
              ┌──────────────────┐
              │ 2. Deterministic │
              │    Normalization │  ← 规则/词典/实体映射，不用 LLM
              └────────┬─────────┘
                       │
                       ▼
              ┌──────────────────┐
              │ 3. Canonical     │
              │    Cache         │──→ Hit ──→ 返回缓存结果
              └────────┬─────────┘
                       │ Miss
                       ▼
              ┌──────────────────┐
              │ 4. Hard OUT      │
              │    Rules         │──→ OUT ──→ 拒答
              └────────┬─────────┘
                       │ PASS
                       ▼
              ┌──────────────────┐
              │ 5. Semantic      │
              │    Coverage      │  ← Embedding: 判断"像不像数据库知识"
              │    Detection     │
              └────────┬─────────┘
                       │
            ┌──────────┼──────────┐
            ▼          ▼          ▼
          CLEAR       GRAY       CLEAR
           OUT                    IN
            │          │           │
            │          ▼           │
            │   ┌───────────┐      │
            │   │ 6. LLM    │      │
            │   │ Evidence  │      │  ← 判断"数据库是否真的能回答"
            │   │ Judge     │      │
            │   └─────┬─────┘      │
            │         │            │
            └─────────┴────────────┘
                      │
                      ▼
                FINAL IN / OUT
```

### 4.2 各层职责

| 层级 | 职责 | 技术手段 | 核心原则 |
| --- | --- | --- | --- |
| Exact Query Cache | 完全相同文本直接返回 | 文本 Hash | 零成本 |
| Deterministic Normalization | 轻量标准化，不做语义推理 | 规则/词典/实体映射 | 不用 LLM |
| Canonical Cache | 相同标准化结果直接返回 | Hash 匹配 | 零成本 |
| Hard OUT Rules | 过滤明显领域外问题 | 关键词/模式匹配 | 可激进 |
| Semantic Coverage Detection | 判断问题"像不像数据库知识" | 多向量 Cosine Similarity | 候选覆盖检测，不是边界检测 |
| LLM Evidence Judge | 灰区问题最终裁决 | 结构化四维度判定 | 仅灰区触发，temperature=0 |

### 4.3 模块依赖

```
cache.ts
    │
    ▼
normalization.ts  (deterministic: 规则 + 词典 + 实体映射)
    │
    ▼
boundary-engine.ts
    │
    ├──► hard-rules.ts        (仅 Hard OUT)
    ├──► embedding-check.ts   (Semantic Coverage Detection)
    └──► llm-judge.ts         (Evidence Judge, 仅灰区)
```

## 5. 第一层：Exact Query Cache

### 5.1 目的

完全相同的文本 → 直接返回缓存结果，零计算成本。

### 5.2 实现

```
cache_key = hash(原始用户问题文本.trim().toLowerCase())
```

- 不做任何预处理
- 不做任何标准化
- 仅精确文本匹配

### 5.3 适用场景

- 用户重复发送相同问题
- 高频问答场景
- 系统重启后依然有效（持久化缓存）

## 6. 第二层：Deterministic Normalization

### 6.1 核心原则

> **不用 LLM 做 Canonicalization。** LLM Canonicalization 本身会成为不一致来源，且让每个请求都付出 LLM 调用的成本。

### 6.2 实现方式

采用纯确定性方法，按优先级依次尝试：

```
Step 1: 实体词典匹配
  ├─ 游戏名称标准化：CS2/CSGO → cs2, VAL/Valorant → valorant
  ├─ 武器名称标准化：AK/AK47/阿卡 → AK-47, M4/M4A4 → M4A4
  ├─ 地图名称标准化：dust2/沙二 → Dust2
  └─ 术语标准化：压枪/控枪 → recoil_control

Step 2: 规则模式匹配
  ├─ 问题类型识别：为什么/为何/为啥 → why, 怎么做/如何/怎么 → how_to
  ├─ 比较词识别：vs/对比/区别/哪个好 → compare
  └─ 预测词识别：会不会/将要/未来/下个赛季 → predict

Step 3: 轻量模型（仅当 Step 1-2 无法确定关键字段时）
  └─ 使用轻量分类模型（非生成式 LLM）做 question_type 分类
```

### 6.3 标准化字段定义

| 字段 | 类型 | 说明 | 示例 |
| --- | --- | --- | --- |
| `domain` | enum | 领域分类 | `shooting_game` |
| `game` | string \| null | 具体游戏 | `CS2`, `Valorant`, `PUBG` |
| `entity` | string \| null | 核心实体 | `AK-47`, `Dust2`, `AWP` |
| `topic` | enum | 知识主题 | `weapon`, `map`, `player_behavior`, `game_mechanic` |
| `intent` | string \| null | 用户意图 | `recoil_control`, `usage_rate`, `preference_reason` |
| `question_type` | enum | 问题类型 | `what`, `how_to`, `why`, `compare`, `predict`, `evaluate` |

### 6.4 标准化示例

```
输入："CS2里面AK到底咋压枪啊？"
       ↓ Step 1: 实体词典
game=CS2, entity=AK-47, intent=recoil_control
       ↓ Step 2: 规则模式
question_type=how_to, topic=weapon
       ↓
输出：
{
  domain: "shooting_game",
  game: "CS2",
  entity: "AK-47",
  topic: "weapon",
  intent: "recoil_control",
  question_type: "how_to"
}
```

```
输入："CS2 的 AK 怎么控制后坐力？"
       ↓ Step 1: 实体词典
game=CS2, entity=AK-47, intent=recoil_control
       ↓ Step 2: 规则模式
question_type=how_to, topic=weapon
       ↓
输出：
{
  domain: "shooting_game",
  game: "CS2",
  entity: "AK-47",
  topic: "weapon",
  intent: "recoil_control",
  question_type: "how_to"
}
```

→ 两个不同表述得到**完全相同**的 Canonical 表示（因为规则和词典是确定性的）。

### 6.5 为什么不用 LLM 做 Canonicalization

| 问题 | 说明 |
| --- | --- |
| 每个请求都调用 LLM | 违背省 Token 目标 |
| LLM 输出不稳定 | 同一问题两次调用可能得到不同 topic/intent |
| 不一致传播 | Canonicalization 不一致 → 后续所有层级走不同路径 |
| 温度=0 也不保证确定性 | 不同 LLM 提供商、不同版本行为不同 |

### 6.6 Topic 枚举（与 Knowledge Coverage Space 对齐）

```
weapon              — 武器属性、机制、使用
map                 — 地图结构、点位、战术
game_mechanic       — 游戏机制、规则、系统
player_behavior     — 玩家行为模式、习惯
player_preference   — 玩家偏好、选择原因
competitive         — 竞技、排位、赛事
KOL_content         — KOL 创作内容、观点
game_mode           — 游戏模式、玩法
economy             — 游戏经济系统
meta                — 版本 Meta、环境
```

### 6.7 Question Type 枚举

```
what            — 事实查询（"是什么"）
how_to          — 方法/操作指导（"怎么做"）
why             — 原因/动机解释（"为什么"）
compare         — 比较分析（"A 和 B 有什么区别"）
predict         — 预测/趋势（"未来会怎样"）
evaluate        — 评价/判断（"好不好"）
```

## 7. 第三层：Canonical Cache + Hard Boundary Rules

### 7.1 Canonical Cache

标准化后的 Canonical Query → Hash → 查找缓存。

```
cache_key = hash(canonical_query_json)
```

命中 → 直接返回历史结果。这与 Exact Query Cache 的区别在于：不同的原始文本，只要标准化后相同，就能命中同一个 Canonical Cache 条目。

### 7.2 Hard OUT Rules（可以激进）

触发任一条件 → 直接 OUT：

| 规则 ID | 条件 | 示例 |
| --- | --- | --- |
| R1 | `domain != "shooting_game"` | "股票怎么买？" |
| R2 | 包含明确非射击游戏关键词 | "王者荣耀"、"原神"、"LOL 英雄" |
| R3 | 包含非游戏领域意图 | "写代码"、"翻译"、"总结" |
| R4 | 攻击性/不当内容 | — |

**Hard OUT 原则**：可以激进。明显领域外的问题，宁可错杀不可放过。

### 7.3 Hard IN Rules（必须极其保守）

> **关键原则**：Hard IN 只允许"可证明的确定性命中"。

| 规则 ID | 条件 | 示例 |
| --- | --- | --- |
| P1 | Canonical Query 完全匹配某条已验证 IN 的缓存记录 | Cache 精确命中 → 已在 Canonical Cache 层处理 |
| P2 | 问题与数据库已有 FAQ 精确匹配 | 预定义且已验证的 FAQ 列表 |

**明确删除的规则**：

> ~~P2: 问题包含已索引的统计指标名称 + 明确游戏 → IN~~

删除原因：**"问题提到了数据库中的东西" ≠ "数据库能够回答这个问题"。**关键词命中不构成 Answerability 的充分条件。例如数据库有"AK 使用率"，用户问"AK 为什么比 M4 更受欢迎"，关键词全部命中但数据库无法回答。

### 7.4 实现方式

纯规则引擎，不依赖 LLM：

```typescript
interface HardRule {
  id: string;
  type: "deny" | "allow";
  condition: (canonical: CanonicalQuery, rawQuery: string) => boolean;
  priority: number;
}
```

- 拒绝规则优先级 > 允许规则
- 所有规则在 5ms 内完成
- 规则配置化，支持热更新

## 8. 第四层：Semantic Coverage Detection（Embedding）

### 8.1 重新定位

> **Embedding 层的职责不是"边界检测"，而是"Candidate Coverage Detection"** — 判断问题"像不像数据库知识"。

它回答的问题是：

> "这个问题在语义上是否接近数据库中的某个知识区域？"

而**不是**：

> "数据库是否能回答这个问题？"

后者由 LLM Evidence Judge 在灰区中判断。

### 8.2 为什么不用全局单向量比较

```
❌ 错误做法：
  整个数据库 → 单一 Centroid → 计算 sim(q, centroid)

✅ 正确做法：
  数据库 → 多个知识区域 → 各自多向量表示 → max(sim(q, region_i))
```

原因：

- 数据库是多个语义区域的集合，不是均匀分布
- 用户问题通常只涉及一个知识区域
- 全局 Centroid 会模糊不同区域的边界

### 8.3 为什么不用单一 Centroid

一个知识区域内部可能不是均匀的球型分布。例如：

```
Weapon 区域
 ├─ AK 系列
 ├─ M4 系列
 ├─ AWP
 ├─ shotgun
 └─ pistol
```

它们的平均 Centroid 可能落在**数据库中不存在的"语义中心"**，导致相似度计算失真。

### 8.4 多向量表示

每个知识区域存储：

```
Region
 ├── centroid           (区域中心向量，mean/medoid)
 ├── representative_1   (典型样本向量)
 ├── representative_2
 ├── ...
 └── hard_negative_1    (语义接近但不可回答的样本向量)
     hard_negative_2
     ...
```

### 8.5 相似度计算

```
给定：
  q = embed(user_question)
  region_i = {
    centroid: C_i,
    representatives: [R_i1, R_i2, ...],
    hard_negatives: [H_i1, H_i2, ...]
  }

计算：
  sim_to_centroid = cosine_similarity(q, C_i)
  sim_to_reps = [cosine_similarity(q, R_ij) for j]
  sim_to_hn = [cosine_similarity(q, H_ij) for j]
  region_score_i = max(sim_to_centroid, max(sim_to_reps))

判定（基于 region_score = max over all regions）：
  if region_score > T_high → CLEAR IN  (语义明确接近数据库知识)
  if region_score < T_low  → CLEAR OUT (语义明确远离数据库知识)
  else                     → GRAY      (进入 LLM Evidence Judge)
```

### 8.6 Hard Negative Vectors 的作用

Hard Negative Vectors 不直接参与 score 计算，但用于：

- 观察 Gray 区域中问题是否异常接近 Hard Negative
- 如果 `sim(q, H_ij) > sim(q, R_ij)`，即使整体 score 在 Gray 区偏高，也应倾向于 OUT
- 用于后续阈值校准和区域边界分析

### 8.7 Embedding Model

- 使用与数据库 Build 阶段相同的 Embedding Model
- V0.1 使用当前系统已有的 Embedding 模型
- Model 版本记录在判定结果中，确保可追溯

## 9. 第五层：Gray Zone LLM Evidence Judge

### 9.1 触发条件

仅当 `T_low ≤ region_score ≤ T_high` 时触发。

### 9.2 设计原则

> **LLM 不自由判断，而是执行结构化 Evidence 判定。Embedding 判断"像不像"，LLM 判断"能不能回答"。**

### 9.3 四维度判定框架（B4 为决定性条件）

```
B1. Domain (领域) — 必要条件
    IN  → 属于射击游戏领域
    OUT → 不属于 → 直接 OUT

B2. Topic Coverage (主题覆盖) — 必要条件
    IN  → 数据库覆盖问题涉及的主题
    OUT → 数据库未覆盖 → 直接 OUT

B3. Question Type Coverage (问题类型覆盖) — 必要条件
    IN  → 数据库支持该问题类型（如事实查询、统计查询）
    OUT → 数据库不支持（如预测、原因推断） → 直接 OUT

B4. Evidence Sufficiency (证据充分性) — 最终决定性条件
    IN  → 数据库存在足够证据支撑回答
    OUT → 证据不足 → 即使 B1-B3 全部 IN，仍为 OUT

Final:
    IN  = B1 ∧ B2 ∧ B3 ∧ B4
    OUT = ¬(B1 ∧ B2 ∧ B3 ∧ B4)
```

**关键层级关系**：

> B1-B3 是必要条件（缺一不可），B4 是最终决定性条件。即使 B1-B3 全部 IN，只要 B4 = OUT，最终就是 OUT。

### 9.4 LLM 调用参数

```
temperature = 0
固定 System Prompt
固定 Boundary Specification（含 Knowledge Coverage Matrix）
固定 Database Coverage Specification
```

### 9.5 Prompt 结构

```text
System:
你是问题边界检测器。你的任务是判断用户问题是否在系统的知识边界内。
你必须严格依据以下规范进行判断，不得依靠你自己的世界知识。

## Boundary Specification
[定义什么是 IN / OUT，四个维度的详细判定标准]

## Knowledge Coverage Matrix
[Region × Intent × Question Type × Evidence → Answerability 矩阵]
这是你判断的核心依据。矩阵中标记为 OUT 的组合，你不得判定为 IN。

## Database Coverage Specification
[列出数据库覆盖的知识区域、主题、问题类型、证据范围]

## 判定规则
1. 每个维度只能输出 IN 或 OUT
2. B1-B3 是必要条件，任一为 OUT → Final = OUT
3. B4 是最终决定性条件：即使 B1-B3 全部 IN，B4=OUT → Final = OUT
4. 如果 Knowledge Coverage Matrix 明确标记为 OUT 的组合 → 直接 OUT
5. 如果数据库覆盖了主题但不支持该问题类型 → B3 = OUT
6. 如果数据库覆盖了主题和问题类型但证据不足 → B4 = OUT

## 输出格式
{
  "B1_domain": "IN" | "OUT",
  "B2_topic_coverage": "IN" | "OUT",
  "B3_question_type_coverage": "IN" | "OUT",
  "B4_evidence_sufficiency": "IN" | "OUT",
  "final": "IN" | "OUT",
  "reasoning": "简要说明判定依据"
}
```

### 9.6 关键约束

- **不允许 LLM 依靠自己的世界知识判断** — 必须依据 Knowledge Coverage Matrix
- **不允许 LLM 给出模糊结论** — 每个维度只能是 IN/OUT
- **不允许 LLM 生成回答** — 仅输出判定结果
- **temperature=0** — 保证可重复性

## 10. Knowledge Coverage Space 设计

### 10.1 概念

Knowledge Coverage Space 是对数据库"能回答什么"的显式建模。其核心产出是 **Knowledge Coverage Matrix**：

```
Region × Intent × Question Type × Evidence → Answerability
```

### 10.2 Knowledge Coverage Matrix（核心）

这是整个 Boundary Engine 的判定依据。矩阵定义每个 (Region, Intent, Question Type) 组合是否被数据库支持。

**示例（部分）**：

### 10.5 多向量计算

对于每个知识区域，从其包含的所有 Segment 的 Embedding 计算：

```
centroid = mean(embed(s) for s in region_segments)
  或 medoid（取与所有其他向量平均相似度最高的向量）

representatives = 聚类后选取 K 个簇中心
  (K 根据区域内 segment 数量和数据分散度决定，初始 K=3~5)

hard_negatives = 人工标注的"语义接近但不可回答"的问题对应的向量
```

### 10.6 维护与更新

- 数据库新增内容 → 更新受影响区域的 vectors
- 新增知识区域 → 定义新的矩阵条目 + vectors
- Coverage Matrix 变更 → 更新 LLM Judge 的 Prompt
- 每次更新 → 递增 `knowledge_space_version`，触发相关 Cache 失效

## 11. 双阈值机制

### 11.1 为什么需要双阈值

```
单阈值问题：
  similarity = 0.76 → IN
  similarity = 0.74 → OUT
  → 边界附近 0.02 的差异决定完全不同的结果，抖动严重

双阈值方案：
  region_score > T_high        → CLEAR IN（语义明确接近数据库知识）
  region_score < T_low         → CLEAR OUT（语义明确远离数据库知识）
  T_low ≤ region_score ≤ T_high → GRAY（进入 LLM Evidence Judge）
```

### 11.2 阈值结构

```
region_score

  0.0                      T_low              T_high              1.0
   │                         │                   │                  │
   ├─────── CLEAR OUT ───────┼───── GRAY ────────┼─── CLEAR IN ────┤
   │                         │                   │                  │
   │  直接拒答               │   LLM 判定        │   直接回答       │
   │  (语义明确远离)          │  (Evidence Judge) │  (语义明确接近)  │
```

### 11.3 阈值确定流程

```
Step 1: 建立 Knowledge Coverage Matrix（先于 Benchmark）
Step 2: 从 Matrix 系统采样构建 Benchmark
Step 3: 对所有 Benchmark 样本计算 region_score
Step 4: 画出 Clear IN / Clear OUT / Hard Negative 的 score 分布
Step 5: 基于分布选择 T_low 和 T_high
Step 6: 在验证集上评估指标
Step 7: 调整阈值直到满足目标
```

### 11.4 阈值选择原则（按优先级排序）

| 优先级 | 原则 | 说明 |
| --- | --- | --- |
| **①** | False Accept Rate 最低 | 首要指标，尤其是 Hard Negative 子集 |
| **②** | Hard Negative False Accept Rate ≤ 目标值 | FA 中最危险的子类 |
| **③** | LLM Call Ratio 可控 | 受 Gray 比例影响，但不是硬性约束 |
| **④** | False Reject Rate 可接受 | 次要指标 |
| **⑤** | 延迟可接受 | 工程约束 |

**灰度比例不作为硬性成功标准**。一个 Gray=35% 但 False Accept=0% 的系统，优于 Gray=10% 但 False Accept=12% 的系统。

### 11.5 区域差异化阈值

V0.1 先使用全局 `T_low` / `T_high`。在 Benchmark 校准后，如果发现不同知识区域的 region_score 分布差异显著，再考虑为每个区域设置独立阈值。

```
V0.1: 全局 T_low / T_high
V0.2: 评估是否需要区域差异化阈值
```

## 12. Result Cache 与一致性保障

### 12.1 双层 Cache 架构

```
Layer 1: Exact Query Cache
  key = hash(原始用户问题文本.trim().toLowerCase())
  命中 → 直接返回（零计算）

Layer 2: Canonical Cache
  key = hash(canonical_query_json)
  命中 → 直接返回（仅经过 Deterministic Normalization）
```

### 12.2 Cache 条目结构

```json
{
  "cache_key": "sha256:abc123...",
  "cache_layer": "canonical",
  "original_queries": ["CS2 AK怎么压枪？", "CS2里面AK咋压枪啊？"],
  "canonical_query": { ... },
  "boundary_result": {
    "final": "IN",
    "method": "embedding",
    "region_score": 0.87,
    "boundary_version": "v0.1",
    "threshold_version": "v0.1-calibration-1",
    "knowledge_space_version": "v0.1",
    "created_at": "2026-08-27T10:00:00Z"
  }
}
```

### 12.3 Cache 失效策略

| 触发条件 | Exact Query Cache | Canonical Cache |
| --- | --- | --- |
| Boundary Version 升级 | 全部失效 | 全部失效 |
| Threshold Version 变更 | 全部失效 | 仅灰区条目失效 |
| Knowledge Coverage Matrix 更新 | 受影响区域条目失效 | 受影响区域条目失效 |
| Embedding Model 变更 | 全部失效 | 全部失效 |
| Deterministic Normalization 词典更新 | 不受影响 | 受影响条目失效 |

### 12.4 一致性保障机制总结

```
┌─────────────────────────────────────────────────────┐
│                  一致性保障层次                       │
│                                                     │
│  1. Exact Query Cache  → 完全相同文本 → 100% 一致    │
│  2. Deterministic Norm  → 规则/词典确定，无随机性     │
│  3. Canonical Cache    → 相同标准化结果 → 100% 一致   │
│  4. temperature=0      → LLM 判定可重复              │
│  5. 固定 Prompt        → 消除 Prompt 漂移             │
│  6. 版本化             → 变更可追溯                   │
└─────────────────────────────────────────────────────┘
```

### 12.5 三级一致性测试

**Level 1：Exact Consistency**

完全相同的文本 → 必须 100% 一致。

```
Q == Q → 结果必须相同
```

**Level 2：Semantic Paraphrase Consistency**

同义改写 → 目标 ≥ 95% 一致。

```
"为什么大家喜欢 AK？"
"AK 为什么这么受欢迎？"
"玩家为何偏好 AK？"
→ 结果应该相同
```

**Level 3：Boundary-Preserving Perturbation**

这是最重要的测试层级。不仅测试"相似问题是否一致"，还测试**"发生关键语义变化时，边界是否正确翻转"**。

```
"CS2 AK 使用率是多少？"     → IN
"CS2 里 AK 的使用比例是多少？" → IN  (应保持不变)

"CS2 AK 使用率是多少？"     → IN
"CS2 玩家为什么喜欢 AK？"    → OUT (应正确翻转)
```

Level 3 比单纯的 paraphrase consistency 更重要，因为它验证的是系统能否**区分"语义相似但 Answerability 不同"的问题**。

## 13. Boundary Calibration Benchmark

### 13.1 目的

为阈值选择和系统评估提供标准化测试集。

### 13.2 设计原则

> **不固定数量，按边界风险覆盖设计。** Benchmark 从 Knowledge Coverage Matrix 系统采样而来，而非人工随意编写。

### 13.3 构建流程

```
Step 1: 完成 Knowledge Coverage Matrix
         ↓
Step 2: 识别矩阵中的边界风险点
         ↓
Step 3: 按边界风险矩阵采样
         ↓
Step 4: 编写具体问题 + 变体
         ↓
Step 5: 人工审核 Expected 标签
```

### 13.4 边界风险覆盖矩阵（决定 Benchmark 结构）

Benchmark 应覆盖以下维度组合，确保各方向边界均匀：

| Domain | Topic | Question Type | Evidence | Expected | 风险等级 | 重点扩展 |
| --- | --- | --- | --- | --- | --- | --- |
| IN | IN | IN | IN | **IN** | 低 | 基础覆盖 |
| IN | IN | IN | OUT | **OUT** | **极高** | **Hard Negative，重点扩展** |
| IN | IN | OUT | IN | **OUT** | 高 | 重点覆盖 |
| IN | IN | OUT | OUT | **OUT** | 中 | 基础覆盖 |
| IN | OUT | IN | IN | **OUT** | 中 | 基础覆盖 |
| IN | OUT | IN | OUT | **OUT** | 低 | 基础覆盖 |
| IN | OUT | OUT | IN | **OUT** | 低 | 基础覆盖 |
| IN | OUT | OUT | OUT | **OUT** | 低 | 基础覆盖 |
| OUT | — | — | — | **OUT** | 低 | 基础覆盖 |

**重点扩展方向**：

- **(IN, IN, IN, OUT) → OUT**：Hard Negative，语义最接近可回答范围但证据不足。这是系统最危险的失败模式，必须大量覆盖。
- **(IN, IN, OUT, IN) → OUT**：数据库有数据但问题类型不支持。系统需要拒绝"问法不对"的问题。

| 优先级 | 指标 | 公式 | 说明 |
| --- | --- | --- | --- |
| **①** | False Accept Rate (FAR) | FA / (FA + TrueReject) | **首要指标** |
| **②** | Hard Negative FAR | FA_HN / (FA_HN + TrueReject_HN) | Hard Negative 子集的 FAR，最关键的细分指标 |
| **③** | LLM Call Ratio | LLMCount / TotalCount | 仅灰区触发 LLM |
| **④** | False Reject Rate (FRR) | FR / (FR + TrueAccept) | 次要指标 |
| **⑤** | Precision | TrueAccept / (TrueAccept + FA) | IN 判定的准确率 |
| **⑥** | Recall | TrueAccept / (TrueAccept + FR) | IN 的召回率 |
| **⑦** | F1 | 2 × P × R / (P + R) | 综合参考 |

### 13.9 相似问题变体测试

为每个测试问题生成变体，验证三个层级的一致性：

| 测试层级 | 变体类型 | 示例 | 期望 |
| --- | --- | --- | --- |
| Level 1 | 完全相同 | 原始问题重复 | 100% 一致 |
| Level 2 | 同义改写 | "玩家偏好 AK 的原因是什么？" | 结果一致 |
| Level 2 | 语序变化 | "AK 在 CS2 中为什么受玩家欢迎？" | 结果一致 |
| Level 2 | 缩写/口语 | "CS2 为啥玩家爱用 AK？" | 结果一致 |
| Level 3 | 关键语义变化（应翻转） | "CS2 AK 使用率是多少？" → "CS2 玩家为什么喜欢 AK？" | IN → OUT 正确翻转 |
| Level 3 | 关键语义变化（应翻转） | "AK 和 M4 哪个使用率高？" → "AK 下赛季会不会削弱？" | IN → OUT 正确翻转 |

## 17. 核心假设与验证计划

### 17.1 三大核心假设

#### H1：IN 与 OUT 的 score distribution 存在可利用的区分度

**假设**：在现有 Embedding 空间中，知识边界内的问题和边界外的问题在 region_score 上有显著差异，可以为双阈值选择提供依据。

> **注意**：不预设具体的相似度数值范围（如 [0.75, 0.95]）。Cosine similarity 的绝对值高度依赖 embedding model、文本格式、中英文、query 长度、prototype 构造方法和数据分布。阈值由 Benchmark 决定，不能从论文中直接迁移。

**验证方法**：
1. 对 Benchmark 所有样本计算 region_score
2. 画出 Clear IN / Clear OUT / Hard Negative 三组的 score 分布
3. 检查分布重叠程度和可分性

**成功标准**：
- Clear IN 和 Clear OUT 的分布存在可见分离
- 可以找到 T_low 和 T_high 使得 False Accept Rate 在可接受范围

**如果失败**（分布严重重叠）：
- 升级 Embedding Model
- 增加 Representative Vectors 数量
- 考虑引入 Mahalanobis distance（V0.2）
- 考虑 Fine-tuned Embedding（V0.3）

#### H2：False Accept Rate 可控制在目标范围内

**假设**：通过双阈值 + 灰区 LLM Judge 的组合，可以将 False Accept Rate（尤其是 Hard Negative 子集）控制在可接受水平。

**验证方法**：
1. 在 Benchmark 上模拟不同阈值组合
2. 计算 False Accept Rate（全局 + Hard Negative 子集）
3. 计算 LLM Call Ratio（用于成本估计）
4. 计算 False Reject Rate（确保在可接受范围）

**成功标准**：
- False Accept Rate（全局）≤ 目标值
- Hard Negative False Accept Rate ≤ 目标值
- False Reject Rate 在可接受范围
- LLM Call Ratio 不构成成本问题

> **注意**：Gray Zone Ratio 不作为硬性成功标准。优先保证 False Accept Rate，而非追求低 Gray 比例。

**如果失败**（False Accept Rate 过高）：
- 调整 T_high 更保守（宁可更多进入灰区）
- 优化 LLM Judge Prompt 和 Knowledge Coverage Matrix
- 考虑增加 Hard Negative Vectors 在判定中的权重

#### H3：相似问题结果一致，关键语义变化时边界正确翻转

**假设**：Deterministic Normalization + 双层 Cache 能保证 Level 1-2 一致性；LLM Judge（temperature=0）能保证 Level 3 的正确翻转。

**验证方法**：
1. 对 Benchmark 中每个问题的所有变体运行 Boundary Engine
2. Level 1: 检查完全相同文本的一致性
3. Level 2: 检查同义改写的一致性
4. Level 3: 检查 Boundary-Flip 变体是否正确翻转

**成功标准**：
```
Level 1 (Exact):            一致性 = 100%
Level 2 (Paraphrase):       一致性 ≥ 95%
Level 3 (Boundary Flip):    正确翻转率 ≥ 95%
```

**如果失败**（一致性不足）：
- Level 1 失败 → Exact Cache 实现有 bug
- Level 2 失败 → Deterministic Normalization 词典/规则不够完善
- Level 3 失败 → LLM Judge 对关键语义变化不够敏感，需优化 Prompt 或 Knowledge Coverage Matrix

### 17.2 验证时间线

```
Week 1-2: Knowledge Coverage Matrix 构建
Week 2-3: Benchmark 构建（从 Matrix 系统采样）
Week 3-4: H1 验证（Score 分布分析）
Week 4-5: H2 验证（False Accept Rate 评估）
Week 5-6: H3 验证（一致性 + 翻转测试）
Week 6:   综合评估报告
```

| 术语 | 英文 | 定义 |
| --- | --- | --- |
| 可回答性 | Answerability | 数据库是否拥有足够证据以支持该问题类型的可靠回答 |

| 灰区 | Gray Zone | region_score 介于两个阈值之间、需要 LLM 判定的区域 |
| 硬负例 | Hard Negative | 语义接近数据库内容但实际超出数据库能力的问题 |
| 假接受 | False Accept | 实际 OUT 但被判定为 IN |
| 假拒绝 | False Reject | 实际 IN 但被判定为 OUT |
| 确定性标准化 | Deterministic Normalization | 用规则/词典/实体映射做标准化，不用 LLM |
| 开放集识别 | Open-Set Recognition | 识别系统需要能够拒绝未知输入，而非强制归类 |
