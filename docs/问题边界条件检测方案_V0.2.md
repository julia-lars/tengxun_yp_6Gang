## V0.1 → V0.2 核心变更

| 编号 | 变更 | 优先级 | 原因 |
| --- | --- | --- | --- |
| 🔴 C1 | **Embedding 不再产出 CLEAR IN**：原 CLEAR IN 降级为 CANDIDATE，必须经过 Knowledge Coverage + Evidence Judge 才能判定最终 IN | **P0** | Embedding 可以证明"可能属于覆盖范围"，但不能单独证明"可回答" |
| 🔴 C2 | **B3 / B4 边界重新定义**：B3 = 系统是否支持该问题类型的回答能力（类型级），B4 = 该具体问题是否有充分证据（实例级） | **P0** | V0.1 中两者边界模糊，容易导致判定不一致 |
| 🔴 C3 | **Canonical Cache 安全性加固**：增加 `answerability_signature` 字段，防止不同可回答性的问题被错误合并 | **P0** | 相同标准化结果 ≠ 相同可回答性（如相同 topic+entity 但不同 intent 的细微差异） |
| 🔴 C4 | **Knowledge Coverage Matrix 扩展**：从 Region × Intent × Question Type × Evidence 扩展为 Region × Intent × Question Type × Evidence Type × Evidence Level → Answerability | **P0** | 原矩阵无法充分表达 evidence 条件的丰富性 |
| 🟠 C5 | **FAR/FRR 指标统一**：全文统一使用 False Accept Rate (FAR) 和 False Reject Rate (FRR)，移除 FPR 等歧义术语 | P1 | 指标定义不一致会导致评估结果不可比 |

## 1. 问题定义

### 1.1 核心问题

（与 V0.1 保持一致，无变更）

当前系统（群体画像 / KOL 分身）在面对用户提问时，**缺乏统一的边界检测机制**。系统可能对以下类型的问题尝试生成回答：

| 问题类型 | 示例 | 风险 |
| --- | --- | --- |
| 明显领域外 | "今天天气怎么样？" | 低风险，容易识别 |
| 领域内但数据库未覆盖 | "CS2 玩家为什么喜欢 AWP？"（数据库只有使用率，无偏好原因） | **高风险** — 语义接近数据库内容，但实际超出证据能力 |
| 领域内但问题类型不支持 | "预测下个赛季 CS2 玩家数量"（数据库只有历史数据，无预测能力） | 中风险 |
| 领域内且有充分证据 | "CS2 玩家使用 AK 的比例是多少？" | 目标回答 |

**核心判断**：

> 这不是一个普通的"相关性分类"问题，而是一个**受限知识域下的 Open-Set Recognition + Knowledge Coverage Detection** 问题。系统需要判断的不是"问题是否相关"，而是"数据库是否具备回答该问题的能力"。

### 1.2 关键区分

```
射击游戏相关 ≠ 数据库可回答
```

系统必须能够区分：

- **Domain IN**（属于射击游戏领域）
- **Knowledge Coverage OUT**（数据库没有覆盖该知识）

这两者之间的差距是 Hard Negative 的主要来源，也是系统最危险的失败模式。

### 1.3 统一入口原则

```
                    Boundary Engine
                         │
                ┌────────┴────────┐
                │                 │
             群体画像            KOL 分身
                │                 │
             Response           Response
```

> **人格决定回答风格，不能决定知识边界。** 同一个问题，无论由 KOL A、KOL B 还是群体画像 C 回答，都必须先经过同一个 Boundary Engine 判定 IN/OUT，然后才允许不同 Persona 生成差异化回答。

## 2. 设计目标与约束

### 2.1 功能目标

| 编号 | 目标 | 说明 |
| --- | --- | --- |
| G1 | 统一边界检测 | 所有问答入口共用同一套 Boundary Engine |
| G2 | 低延迟 | 大部分 OUT 问题通过规则/Embedding 直接判定，不经过 LLM |
| G3 | 低成本 | Canonicalization 不用 LLM；仅灰区问题调用 LLM Judge |
| G4 | 高一致性 | 相同 / 相似问题得到相同边界结果；关键语义变化时边界正确翻转 |
| G5 | 可校准 | 阈值通过 Benchmark 校准，不人工拍定 |
| G6 | 可演进 | 支持版本化：Boundary Version、Threshold Version、Embedding Model Version |

### 2.2 错误优先级（按优先级排序）

| 优先级 | 错误类型 | 含义 |
| --- | --- | --- |
| **① 最高** | False Accept (FA) | 实际 OUT，判为 IN → 系统对边界外内容生成回答 |
| **② 高** | Hard Negative FA | 语义接近数据库内容但实际 OUT，仍判为 IN — FA 中最危险的子类 |
| **③ 中** | False Reject (FR) | 实际 IN，判为 OUT → 系统拒答本可回答的问题 |

> 阈值选择不以最高 Accuracy 为目标，而是以**低 False Accept Rate（尤其是 Hard Negative 子集）**为首要约束。

### 2.3 性能目标

| 指标 | 目标 |
| --- | --- |
| LLM 调用比例 | 仅灰区问题调用 LLM Judge（目标：LLM 不出现在 Canonicalization 或快速路径中） |
| 单次判定延迟（非 LLM 路径） | < 50ms |
| 单次判定延迟（LLM 路径） | < 2s |

## 3. 核心概念：Evidence-Backed Answerability

### 3.1 定义

> **Answerability** = 数据库是否拥有足够证据，以支持该问题类型的可靠回答。

这不是"数据库有没有相关内容"（Semantic Match），而是"数据库能否回答这个问题"（Evidence-Backed Answerability）。

### 3.2 示例

数据库包含：

```
AK 使用率 = 43%
M4 使用率 = 37%
```

| 用户问题 | Semantic Match | Answerability | 判定 |
| --- | --- | --- | --- |
| "AK 使用率是多少？" | ✅ 高 | ✅ 有证据 | **IN** |
| "AK 和 M4 哪个使用率更高？" | ✅ 高 | ✅ 有证据（可比较） | **IN** |
| "AK 为什么比 M4 更受欢迎？" | ✅ 高 | ❌ 无证据（无偏好原因数据） | **OUT** |
| "下一版本 AK 会不会削弱？" | ✅ 中 | ❌ 无证据（无预测能力） | **OUT** |

### 3.3 判定模型（V0.2 修正）

```
                    Question
                       │
              ┌────────┴────────┐
              │                 │
         Semantic Match      Evidence
         (像不像数据库知识)    (能不能回答)
              │                 │
              │    ┌────────────┘
              │    │
              ▼    ▼
         Candidate Coverage Detection
         (Embedding: 判断候选覆盖范围)
              │
              │  CANDIDATE / GRAY
              ▼
         Knowledge Coverage Check
         (Matrix: 判断知识覆盖条件)
              │
              ▼
         Evidence Judge
         (LLM: 判断证据充分性)
              │
              ▼
         FINAL IN / OUT
```

**关键原则（V0.2 新增）**：

> **Embedding 可以证明"可能属于覆盖范围"，但不能单独证明"可回答"。**
>
> **Embedding 可以证明"明确不属于覆盖范围"（CLEAR OUT），可以直接拒答。**
>
> **最终 IN 判定必须经过 Knowledge Coverage + Evidence Judge 双重验证。**

### 3.4 各层在 Answerability 判定中的角色

| 层级 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| Hard OUT Rules | 问题明确不属于射击游戏领域 → OUT | 领域内但不可回答 → 不能判定 |
| Embedding | 问题语义明确远离数据库知识 → OUT | 语义接近 → 只是 CANDIDATE，不能直接判定 IN |
| Embedding | 问题语义接近数据库知识 → CANDIDATE | CANDIDATE ≠ IN，仍需证据验证 |
| Knowledge Coverage Matrix | 问题类型是否被数据库支持 → 类型级过滤 | 具体实例的证据充分性 → 不能判定 |
| Evidence Judge | 该具体问题是否有充分证据 → 最终 IN/OUT | 不需要判定领域相关性（已由上层处理） |

### 4.2 各层职责（V0.2 修正）

| 层级 | 职责 | 技术手段 | 核心原则 | V0.1→V0.2 变更 |
| --- | --- | --- | --- | --- |
| Exact Query Cache | 完全相同文本直接返回 | 文本 Hash | 零成本 | 无变更 |
| Deterministic Normalization | 轻量标准化，不做语义推理 | 规则/词典/实体映射 | 不用 LLM | 无变更 |
| Canonical Cache | 相同标准化结果直接返回 | Hash 匹配 + `answerability_signature` 校验 | 零成本，安全合并 | 🔴 C3: 增加签名校验 |
| Hard OUT Rules | 过滤明显领域外问题 | 关键词/模式匹配 | 可激进 | 无变更 |
| Semantic Candidate Coverage | 判断问题候选覆盖范围 | 多向量 Cosine Similarity | **候选覆盖检测，不是边界检测** | 🔴 C1: CLEAR IN → CANDIDATE |
| Knowledge Coverage Check | 基于 Matrix 做类型级过滤 | Matrix 查表 | 确定性过滤，无 LLM | 🔴 C4: Matrix 扩展 |
| LLM Evidence Judge | 最终裁决 | 结构化四维度判定 | 仅非 CLEAR OUT 触发，temperature=0 | 🔴 C1: 触发范围扩大 |

## 5. 第一层：Exact Query Cache

（与 V0.1 保持一致，无变更）

### 5.1 目的

完全相同的文本 → 直接返回缓存结果，零计算成本。

### 5.2 实现

```
cache_key = hash(原始用户问题文本.trim().toLowerCase())
```

- 不做任何预处理
- 不做任何标准化
- 仅精确文本匹配

### 5.3 适用场景

- 用户重复发送相同问题
- 高频问答场景
- 系统重启后依然有效（持久化缓存）

## 6. 第二层：Deterministic Normalization

（与 V0.1 保持一致，无变更）

### 6.1 核心原则

> **不用 LLM 做 Canonicalization。** LLM Canonicalization 本身会成为不一致来源，且让每个请求都付出 LLM 调用的成本。

### 6.2 实现方式

采用纯确定性方法，按优先级依次尝试：

```
Step 1: 实体词典匹配
  ├─ 游戏名称标准化：CS2/CSGO → cs2, VAL/Valorant → valorant
  ├─ 武器名称标准化：AK/AK47/阿卡 → AK-47, M4/M4A4 → M4A4
  ├─ 地图名称标准化：dust2/沙二 → Dust2
  └─ 术语标准化：压枪/控枪 → recoil_control

Step 2: 规则模式匹配
  ├─ 问题类型识别：为什么/为何/为啥 → why, 怎么做/如何/怎么 → how_to
  ├─ 比较词识别：vs/对比/区别/哪个好 → compare
  └─ 预测词识别：会不会/将要/未来/下个赛季 → predict

Step 3: 轻量模型（仅当 Step 1-2 无法确定关键字段时）
  └─ 使用轻量分类模型（非生成式 LLM）做 question_type 分类
```

### 6.3 标准化字段定义

| 字段 | 类型 | 说明 | 示例 |
| --- | --- | --- | --- |
| `domain` | enum | 领域分类 | `shooting_game` |
| `game` | string \| null | 具体游戏 | `CS2`, `Valorant`, `PUBG` |
| `entity` | string \| null | 核心实体 | `AK-47`, `Dust2`, `AWP` |
| `topic` | enum | 知识主题 | `weapon`, `map`, `player_behavior`, `game_mechanic` |
| `intent` | string \| null | 用户意图 | `recoil_control`, `usage_rate`, `preference_reason` |
| `question_type` | enum | 问题类型 | `what`, `how_to`, `why`, `compare`, `predict`, `evaluate` |

### 6.4 标准化示例

```
输入："CS2里面AK到底咋压枪啊？"
       ↓ Step 1: 实体词典
game=CS2, entity=AK-47, intent=recoil_control
       ↓ Step 2: 规则模式
question_type=how_to, topic=weapon
       ↓
输出：
{
  domain: "shooting_game",
  game: "CS2",
  entity: "AK-47",
  topic: "weapon",
  intent: "recoil_control",
  question_type: "how_to"
}
```

```
输入："CS2 的 AK 怎么控制后坐力？"
       ↓ Step 1: 实体词典
game=CS2, entity=AK-47, intent=recoil_control
       ↓ Step 2: 规则模式
question_type=how_to, topic=weapon
       ↓
输出：
{
  domain: "shooting_game",
  game: "CS2",
  entity: "AK-47",
  topic: "weapon",
  intent: "recoil_control",
  question_type: "how_to"
}
```

→ 两个不同表述得到**完全相同**的 Canonical 表示（因为规则和词典是确定性的）。

### 6.5 为什么不用 LLM 做 Canonicalization

| 问题 | 说明 |
| --- | --- |
| 每个请求都调用 LLM | 违背省 Token 目标 |
| LLM 输出不稳定 | 同一问题两次调用可能得到不同 topic/intent |
| 不一致传播 | Canonicalization 不一致 → 后续所有层级走不同路径 |
| 温度=0 也不保证确定性 | 不同 LLM 提供商、不同版本行为不同 |

### 6.6 Topic 枚举（与 Knowledge Coverage Space 对齐）

```
weapon              — 武器属性、机制、使用
map                 — 地图结构、点位、战术
game_mechanic       — 游戏机制、规则、系统
player_behavior     — 玩家行为模式、习惯
player_preference   — 玩家偏好、选择原因
competitive         — 竞技、排位、赛事
KOL_content         — KOL 创作内容、观点
game_mode           — 游戏模式、玩法
economy             — 游戏经济系统
meta                — 版本 Meta、环境
```

### 6.7 Question Type 枚举

```
what            — 事实查询（"是什么"）
how_to          — 方法/操作指导（"怎么做"）
why             — 原因/动机解释（"为什么"）
compare         — 比较分析（"A 和 B 有什么区别"）
predict         — 预测/趋势（"未来会怎样"）
evaluate        — 评价/判断（"好不好"）
```

## 7. 第三层：Canonical Cache + Hard Boundary Rules

### 7.1 Canonical Cache（🔴 C3 修正）

标准化后的 Canonical Query → Hash → 查找缓存。

```
cache_key = hash(canonical_query_json)
```

**V0.2 新增：`answerability_signature` 校验**

> **问题**：两个不同的原始问题，标准化后可能得到相同的 Canonical Query（如同一 game+entity+topic+intent+question_type），但它们的可回答性可能不同。例如：
>
> - "CS2 中 AK 怎么压枪？" → `{game:CS2, entity:AK-47, intent:recoil_control, question_type:how_to}`
> - "CS2 中 AK 压枪有什么高级技巧？" → `{game:CS2, entity:AK-47, intent:recoil_control, question_type:how_to}`
>
> 两个问题的 Canonical Query 完全相同，但"高级技巧"可能超出数据库覆盖范围。

**解决方案**：Canonical Cache 增加 `answerability_signature` 字段：

```typescript
interface CanonicalCacheEntry {
  cache_key: string;                    // hash(canonical_query_json)
  canonical_query: CanonicalQuery;
  answerability_signature: string;      // 🔴 V0.2 新增
  // ...
}
```

**`answerability_signature` 计算规则**：

```
answerability_signature = hash(
  canonical_query_json +
  detected_entity_type +        // 实体类型（武器/地图/机制/...）
  question_subtype +            // 问题子类型（如 how_to 的 basic/advanced）
  has_modifier_keywords         // 是否包含修饰词（高级/最新/最全/...）
)
```

**校验规则**：

1. Canonical Cache 命中 → 提取 `answerability_signature`
2. 重新计算当前 query 的 `answerability_signature`
3. 签名匹配 → 返回缓存结果
4. 签名不匹配 → **Cache Miss**，进入下游判定流程

**签名不匹配的典型场景**：

| 缓存中的 Query | 新 Query | Canonical 相同？ | 签名相同？ | 处理 |
| --- | --- | --- | --- | --- |
| "AK 怎么压枪？" | "AK 压枪有什么高级技巧？" | ✅ | ❌（有修饰词） | MISS → 重新判定 |
| "M4 使用率多少？" | "M4 为什么受欢迎？" | ❌（question_type 不同） | ❌ | MISS → 重新判定 |
| "AK 怎么压枪？" | "AK 如何控制后坐力？" | ✅ | ✅ | HIT → 返回缓存 |

### 7.2 Hard OUT Rules（可以激进）

（与 V0.1 保持一致）

触发任一条件 → 直接 OUT：

| 规则 ID | 条件 | 示例 |
| --- | --- | --- |
| R1 | `domain != "shooting_game"` | "股票怎么买？" |
| R2 | 包含明确非射击游戏关键词 | "王者荣耀"、"原神"、"LOL 英雄" |
| R3 | 包含非游戏领域意图 | "写代码"、"翻译"、"总结" |
| R4 | 攻击性/不当内容 | — |

**Hard OUT 原则**：可以激进。明显领域外的问题，宁可错杀不可放过。

### 7.3 Hard IN Rules（必须极其保守）

> **关键原则**：Hard IN 只允许"可证明的确定性命中"。

| 规则 ID | 条件 | 示例 |
| --- | --- | --- |
| P1 | Canonical Query 完全匹配某条已验证 IN 的缓存记录 + `answerability_signature` 匹配 | Cache 精确命中 → 已在 Canonical Cache 层处理 |
| P2 | 问题与数据库已有 FAQ 精确匹配 | 预定义且已验证的 FAQ 列表 |

**明确删除的规则**：

> ~~P2: 问题包含已索引的统计指标名称 + 明确游戏 → IN~~

删除原因：**"问题提到了数据库中的东西" ≠ "数据库能够回答这个问题"。**关键词命中不构成 Answerability 的充分条件。例如数据库有"AK 使用率"，用户问"AK 为什么比 M4 更受欢迎"，关键词全部命中但数据库无法回答。

### 7.4 实现方式

纯规则引擎，不依赖 LLM：

```typescript
interface HardRule {
  id: string;
  type: "deny" | "allow";
  condition: (canonical: CanonicalQuery, rawQuery: string) => boolean;
  priority: number;
}
```

- 拒绝规则优先级 > 允许规则
- 所有规则在 5ms 内完成
- 规则配置化，支持热更新

## 8. 第四层：Semantic Candidate Coverage Detection（Embedding）

### 8.1 重新定位（🔴 C1 核心修正）

> **Embedding 层的职责不是"边界检测"，而是"Candidate Coverage Detection"** — 判断问题"像不像数据库知识"。

它回答的问题是：

> "这个问题在语义上是否接近数据库中的某个知识区域？"

而**不是**：

> "数据库是否能回答这个问题？"

后者由 Knowledge Coverage Check + Evidence Judge 共同判断。

### 8.2 V0.1 的核心设计冲突（已修正）

**V0.1 的矛盾**：

```
V0.1 第 8.1 节规定：
  "Embedding 层的职责不是'边界检测'，而是'Candidate Coverage Detection'"

V0.1 第 8.5 节又规定：
  "region_score > T_high → CLEAR IN（语义明确接近数据库知识）"

→ 这实际上让 Embedding 直接决定了 IN，违背了 Candidate Coverage Detection 的定位。
```

**V0.2 修正**：

```
Embedding 判定结果：
  region_score < T_low   → CLEAR OUT  → 直接拒答
  region_score ≥ T_low   → CANDIDATE  → 进入 Knowledge Coverage + Evidence Judge
```

> **Embedding 可以证明"明确 OUT"，但不能证明"最终 IN"。**
>
> **CANDIDATE 的含义**：该问题在语义上可能与数据库知识相关，是候选可回答问题。但最终是否为 IN，必须由下游的 Knowledge Coverage 和 Evidence Judge 决定。

### 8.3 为什么没有 "CLEAR IN" 了

| 场景 | V0.1 处理 | V0.2 处理 | 原因 |
| --- | --- | --- | --- |
| "AK 使用率是多少？" | Embedding → CLEAR IN → IN | Embedding → CANDIDATE → Matrix → Evidence Judge → IN | 即使语义高度匹配，仍需验证数据库确实有该数据 |
| "AK 为什么比 M4 更受欢迎？" | Embedding → CLEAR IN → IN（❌ 错误！） | Embedding → CANDIDATE → Matrix → "why" 类型 OUT → OUT | 语义匹配但无证据，V0.1 会错误接受 |
| "下赛季 AK 会不会削弱？" | Embedding → GRAY → LLM Judge → OUT | Embedding → CANDIDATE → Matrix → "predict" 类型 OUT → OUT | V0.2 通过 Matrix 更快判定 |
| "今天天气怎么样？" | Embedding → CLEAR OUT → OUT | Embedding → CLEAR OUT → OUT | 无变更，明确 OUT 直接拒答 |

### 8.4 为什么不用全局单向量比较

```
❌ 错误做法：
  整个数据库 → 单一 Centroid → 计算 sim(q, centroid)

✅ 正确做法：
  数据库 → 多个知识区域 → 各自多向量表示 → max(sim(q, region_i))
```

原因：

- 数据库是多个语义区域的集合，不是均匀分布
- 用户问题通常只涉及一个知识区域
- 全局 Centroid 会模糊不同区域的边界

### 8.5 为什么不用单一 Centroid

一个知识区域内部可能不是均匀的球型分布。例如：

```
Weapon 区域
 ├─ AK 系列
 ├─ M4 系列
 ├─ AWP
 ├─ shotgun
 └─ pistol
```

它们的平均 Centroid 可能落在**数据库中不存在的"语义中心"**，导致相似度计算失真。

### 8.6 多向量表示

每个知识区域存储：

```
Region
 ├── centroid           (区域中心向量，mean/medoid)
 ├── representative_1   (典型样本向量)
 ├── representative_2
 ├── ...
 └── hard_negative_1    (语义接近但不可回答的样本向量)
     hard_negative_2
     ...
```

### 8.7 相似度计算（V0.2 修正）

```
给定：
  q = embed(user_question)
  region_i = {
    centroid: C_i,
    representatives: [R_i1, R_i2, ...],
    hard_negatives: [H_i1, H_i2, ...]
  }

计算：
  sim_to_centroid = cosine_similarity(q, C_i)
  sim_to_reps = [cosine_similarity(q, R_ij) for j]
  sim_to_hn = [cosine_similarity(q, H_ij) for j]
  region_score_i = max(sim_to_centroid, max(sim_to_reps))

判定（基于 region_score = max over all regions）：
  if region_score < T_low  → CLEAR OUT (语义明确远离数据库知识)
  if region_score ≥ T_low  → CANDIDATE (进入下游判定)
```

### 8.8 Hard Negative Vectors 的作用

Hard Negative Vectors 不直接参与 score 计算，但用于：

- 观察 CANDIDATE 区域中问题是否异常接近 Hard Negative
- 如果 `sim(q, H_ij) > sim(q, R_ij)`，即使整体 score 较高，也应标记为 `hn_proximity_warning`
- `hn_proximity_warning` 作为额外信号传递给 Evidence Judge
- 用于后续阈值校准和区域边界分析

### 8.9 Embedding Model

- 使用与数据库 Build 阶段相同的 Embedding Model
- V0.2 使用当前系统已有的 Embedding 模型
- Model 版本记录在判定结果中，确保可追溯

## 9. 第五层：Knowledge Coverage Check

### 9.1 定位（🔴 C4 扩展）

> **Knowledge Coverage Check 是 Embedding 和 Evidence Judge 之间的类型级过滤器。**
>
> 它的职责是：基于 Knowledge Coverage Matrix，快速判断"该问题类型是否被数据库支持"。
> 它是一个**确定性查表操作**，不涉及 LLM。

### 9.2 触发条件

所有 Embedding 判定为 CANDIDATE 的问题（即 `region_score ≥ T_low`）。

### 9.3 判定逻辑

```
输入：Canonical Query = {region, intent, question_type}
                    + Embedding info = {top_region, region_score, hn_proximity_warning}

Step 1: 确定知识区域
  region = canonical_query.topic 或 embedding.top_region

Step 2: 查 Knowledge Coverage Matrix
  matrix_result = MATRIX[region][intent][question_type]

Step 3: 判定
  if matrix_result.answerability == "OUT" → MATRIX OUT → 直接 OUT
  if matrix_result.answerability == "IN"  → MATRIX IN  → 进入 Evidence Judge
  if matrix_result.answerability == "TBD" → MATRIX TBD → 进入 Evidence Judge（需 LLM 判断）
```

### 9.4 三种 Matrix 结果的处理

| Matrix 结果 | 含义 | 处理 | 示例 |
| --- | --- | --- | --- |
| MATRIX OUT | 该组合明确不被数据库支持 | 直接 OUT，不进入 LLM | `(weapon, usage_rate, why)` = OUT |
| MATRIX IN | 该组合被数据库支持 | 进入 Evidence Judge 做最终验证 | `(weapon, usage_rate, what)` = IN |
| MATRIX TBD | 该组合的支持状态待定 | 进入 Evidence Judge 由 LLM 判断 | `(weapon, preference, what)` = TBD |

### 9.5 Knowledge Coverage Check 的边界

**Knowledge Coverage Check 不能替代 Evidence Judge**：

- Matrix 告诉你"这种问题类型原则上有数据支持"
- 但不能告诉你"这个具体问题是否有充分证据"
- 例如：Matrix 说 `(weapon, usage_rate, what) = IN`，但用户问的是"AK-47 在 2024 年 3 月 15 日下午的使用率"，数据库可能没有这么细粒度的数据
- 这种情况下，Matrix 返回 MATRIX IN，但 Evidence Judge 应该判定为 OUT

## 10. 第六层：Gray Zone LLM Evidence Judge

### 10.1 触发条件（🔴 C1 修正）

**V0.1**：仅当 `T_low ≤ region_score ≤ T_high` 时触发。

**V0.2**：当以下条件同时满足时触发：
1. Embedding 判定为 CANDIDATE（`region_score ≥ T_low`）
2. Knowledge Coverage Check 判定为 MATRIX IN 或 MATRIX TBD

### 10.2 设计原则

> **LLM 不自由判断，而是执行结构化 Evidence 判定。Embedding 判断"像不像"，Matrix 判断"类型是否支持"，LLM 判断"具体能不能回答"。**

### 10.3 四维度判定框架（🔴 C2 修正）

```
B1. Domain (领域) — 必要条件
    IN  → 属于射击游戏领域
    OUT → 不属于 → 直接 OUT
    判定依据：canonical_query.domain + 用户问题内容

B2. Topic Coverage (主题覆盖) — 必要条件
    IN  → 数据库覆盖问题涉及的主题
    OUT → 数据库未覆盖 → 直接 OUT
    判定依据：canonical_query.topic 是否在数据库覆盖范围内

B3. Question Type Capability (问题类型能力) — 必要条件（🔴 C2 重新定义）
    IN  → 系统具备回答该问题类型的**能力**（即该类型的问题在原则上有数据支持）
    OUT → 系统不具备该能力 → 直接 OUT
    判定依据：Knowledge Coverage Matrix 中该 (region, intent, question_type) 组合是否被支持
    **关键区分**：B3 判断的是"类型级能力"，而非"实例级证据"。例如：
    - "数据库是否有能力回答关于武器使用率的 what 问题" → B3 关注
    - "数据库是否有 AK-47 在特定条件下的使用率数据" → 这是 B4 关注

B4. Evidence Sufficiency (证据充分性) — 最终决定性条件（🔴 C2 重新定义）
    IN  → 对于**该具体问题实例**，数据库存在足够证据支撑回答
    OUT → 证据不足 → 即使 B1-B3 全部 IN，仍为 OUT
    判定依据：该问题的具体实体、条件、粒度是否在数据库中有对应证据
    **关键区分**：B4 判断的是"实例级证据"，而非"类型级能力"。例如：
    - "AK-47 的使用率数据是否存在" → B4 关注
    - "数据库是否有能力回答 about 使用率的问题" → 这是 B3 关注

Final:
    IN  = B1 ∧ B2 ∧ B3 ∧ B4
    OUT = ¬(B1 ∧ B2 ∧ B3 ∧ B4)
```

### 10.4 B3 vs B4 的边界示例（🔴 C2 新增）

| 场景 | B3 (类型级能力) | B4 (实例级证据) | 最终 |
| --- | --- | --- | --- |
| "AK-47 使用率是多少？" | IN（系统支持 what 类型使用率查询） | IN（有 AK-47 使用率数据） | **IN** |
| "AK-47 为什么受欢迎？" | OUT（系统不支持 why 类型偏好查询） | OUT（无偏好原因数据） | **OUT** |
| "M4A1-S 使用率是多少？" | IN（系统支持 what 类型使用率查询） | IN（有 M4A1-S 使用率数据） | **IN** |
| "AK-47 在 2024 年 3 月的使用率？" | IN（系统支持 what 类型使用率查询） | OUT（无按月粒度数据） | **OUT** |
| "下赛季什么武器会变强？" | OUT（系统不支持 predict 类型） | OUT（无预测能力） | **OUT** |
| "CS2 玩家和 Valorant 玩家在武器偏好上有什么不同？" | IN（系统支持 compare 类型） | TBD（跨游戏比较数据可能存在） | 需 LLM 判断 |

### 10.5 LLM 调用参数

```
temperature = 0
固定 System Prompt
固定 Boundary Specification（含 Knowledge Coverage Matrix）
固定 Database Coverage Specification
```

### 10.6 Prompt 结构（V0.2 修正）

```text
System:
你是问题边界检测器。你的任务是判断用户问题是否在系统的知识边界内。
你必须严格依据以下规范进行判断，不得依靠你自己的世界知识。

## Boundary Specification
[定义什么是 IN / OUT，四个维度的详细判定标准]

## Knowledge Coverage Matrix
[Region × Intent × Question Type × Evidence Type × Evidence Level → Answerability 矩阵]
这是你判断的核心依据。矩阵中标记为 OUT 的组合，你不得判定为 IN。

## Database Coverage Specification
[列出数据库覆盖的知识区域、主题、问题类型、证据范围、证据粒度]

## Embedding 信号
- top_region: {region_name}
- region_score: {score}
- hn_proximity_warning: {true/false}  (是否异常接近 Hard Negative)

## 判定规则
1. 每个维度只能输出 IN 或 OUT
2. B1-B3 是必要条件，任一为 OUT → Final = OUT
3. B4 是最终决定性条件：即使 B1-B3 全部 IN，B4=OUT → Final = OUT
4. B3 判断的是"类型级能力"：系统是否支持该问题类型。参考 Knowledge Coverage Matrix
5. B4 判断的是"实例级证据"：该具体问题是否有充分证据。考虑问题的具体实体、条件、粒度
6. 如果 Knowledge Coverage Matrix 明确标记为 OUT 的组合 → 直接 OUT
7. 如果 hn_proximity_warning = true，应更严格地审视 B4 判定

## 输出格式
{
  "B1_domain": "IN" | "OUT",
  "B2_topic_coverage": "IN" | "OUT",
  "B3_question_type_capability": "IN" | "OUT",
  "B4_evidence_sufficiency": "IN" | "OUT",
  "final": "IN" | "OUT",
  "reasoning": "简要说明判定依据，特别说明 B3 vs B4 的区分"
}
```

### 10.7 关键约束

- **不允许 LLM 依靠自己的世界知识判断** — 必须依据 Knowledge Coverage Matrix
- **不允许 LLM 给出模糊结论** — 每个维度只能是 IN/OUT
- **不允许 LLM 生成回答** — 仅输出判定结果
- **temperature=0** — 保证可重复性
- **必须区分 B3（类型级）和 B4（实例级）** — 在 reasoning 中明确说明

## 11. Knowledge Coverage Space 设计（V0.2 扩展）

### 11.1 概念

Knowledge Coverage Space 是对数据库"能回答什么"的显式建模。其核心产出是 **Knowledge Coverage Matrix**：

```
Region × Intent × Question Type × Evidence Type × Evidence Level → Answerability
```

### 11.2 Knowledge Coverage Matrix（🔴 C4 扩展）

**V0.1 矩阵维度**：`Region × Intent × Question Type × Evidence → Answerability`

**V0.2 矩阵维度**：`Region × Intent × Question Type × Evidence Type × Evidence Level → Answerability`

**新增维度说明**：

| 维度 | 说明 | 取值示例 |
| --- | --- | --- |
| Evidence Type | 证据的类型 | `statistical`（统计数据）、`qualitative`（定性描述）、`comparative`（对比数据）、`temporal`（时序数据） |
| Evidence Level | 证据的粒度/置信度 | `aggregated`（聚合级）、`segmented`（分段级）、`individual`（个体级） |

**示例（部分）**：

| Region | Intent | Question Type | Evidence Type | Evidence Level | Answerability |
| --- | --- | --- | --- | --- | --- |
| weapon | usage_rate | what | statistical | aggregated | **IN** |
| weapon | usage_rate | what | statistical | segmented | **IN** |
| weapon | usage_rate | what | statistical | individual | **OUT**（无个体级数据） |
| weapon | usage_rate | compare | comparative | aggregated | **IN** |
| weapon | usage_rate | why | — | — | **OUT**（无原因数据） |
| weapon | usage_rate | predict | — | — | **OUT**（无预测能力） |
| weapon | recoil_control | what | qualitative | aggregated | **IN** |
| weapon | recoil_control | how_to | qualitative | aggregated | **IN** |
| weapon | recoil_control | why | — | — | **OUT** |
| weapon | preference | what | statistical | aggregated | **TBD** |
| weapon | preference | why | — | — | **OUT** |
| weapon | preference | predict | — | — | **OUT** |
| map | callouts | what | qualitative | aggregated | **IN** |
| map | callouts | how_to | qualitative | aggregated | **IN** |
| map | strategy | what | qualitative | aggregated | **IN** |
| map | strategy | why | — | — | **OUT** |
| map | strategy | predict | — | — | **OUT** |
| player_behavior | play_pattern | what | statistical | aggregated | **IN** |
| player_behavior | play_pattern | what | statistical | segmented | **IN**（按段位分段） |
| player_behavior | play_pattern | compare | comparative | aggregated | **IN** |
| player_behavior | play_pattern | why | — | — | **OUT** |
| player_behavior | motivation | what | — | — | **OUT**（无动机数据） |
| player_behavior | motivation | why | — | — | **OUT** |
| competitive | rank_distribution | what | statistical | aggregated | **IN** |
| competitive | rank_distribution | compare | comparative | aggregated | **IN** |
| competitive | meta | what | qualitative | aggregated | **IN** |
| competitive | meta | predict | — | — | **OUT** |

**矩阵构建原则**：

1. 遍历每个知识区域
2. 列出该区域包含的所有 Intent
3. 对每个 Intent，列出所有 Question Type
4. 对每个 Question Type，列出可能的 Evidence Type 和 Evidence Level
5. 逐一判断数据库是否具备该组合的证据
6. 不确定的标记为"TBD"，后续通过人工审核确定

### 11.3 知识区域定义

每个知识区域包含：

| 属性 | 说明 |
| --- | --- |
| `region_id` | 唯一标识 |
| `region_name` | 区域名称（如 weapon、map） |
| `coverage_matrix` | Region × Intent × Question Type × Evidence Type × Evidence Level → Answerability 映射 |
| `centroid_vector` | 区域中心向量（mean/medoid） |
| `representative_vectors` | 典型样本向量列表（多个，不只一个） |
| `hard_negative_vectors` | 语义接近但不可回答的样本向量 |
| `coverage_description` | 人类可读的覆盖范围描述 |
| `sample_queries` | 该区域典型可回答的问题示例 |
| `hard_negative_examples` | 该区域语义接近但不可回答的问题示例 |

### 11.5 多向量计算

对于每个知识区域，从其包含的所有 Segment 的 Embedding 计算：

```
centroid = mean(embed(s) for s in region_segments)

```

## 12. 双阈值机制（V0.2 修正）

### 12.1 为什么需要双阈值（🔴 C1 修正）

**V0.1 的双阈值**：
```
region_score > T_high        → CLEAR IN（直接回答）
T_low ≤ region_score ≤ T_high → GRAY（LLM 判定）
region_score < T_low         → CLEAR OUT（直接拒答）
```

**V0.1 的问题**：CLEAR IN 路径让 Embedding 直接决定 IN，违背了"Embedding 不单独证明可回答性"的原则。

**V0.2 的双阈值（修正后）**：
```
region_score ≥ T_low         → CANDIDATE（进入下游判定）
region_score < T_low         → CLEAR OUT（直接拒答）
```

> **V0.2 中 T_high 不再作为 CLEAR IN 的阈值。** T_high 保留但降级为内部信号：用于区分 CANDIDATE 的置信度高低，但不改变判定路径。高置信度 CANDIDATE 和低置信度 CANDIDATE 都经过相同的下游流程。

### 12.2 阈值结构（V0.2 修正）

```
region_score

  0.0                      T_low              T_high              1.0
   │                         │                   │                  │
   ├─────── CLEAR OUT ───────┼─── CANDIDATE ───────────────────────┤
   │                         │                   │                  │
   │  直接拒答               │   进入 Knowledge Coverage + Evidence Judge      │
   │  (语义明确远离)          │   (候选可回答，需要证据验证)                    │
```

**T_high 的保留用途**：

- 监控指标：统计 "高置信度 CANDIDATE" 的比例
- 评估 Matrix 效率：如果大量高置信度 CANDIDATE 最终被 Matrix 判定为 MATRIX OUT，说明 Matrix 覆盖不足
- 评估 Evidence Judge 效率：如果大量高置信度 CANDIDATE 最终被 Evidence Judge 判定为 OUT，说明 Embedding 与 Evidence 之间存在系统性偏差
- 未来优化：如果 Matrix 和 Evidence Judge 表现稳定，高置信度 CANDIDATE 的 MATRIX IN 路径可以考虑在 V0.3+ 中优化为快速路径

### 12.3 阈值确定流程

```
Step 1: 建立 Knowledge Coverage Matrix（先于 Benchmark）
Step 2: 从 Matrix 系统采样构建 Benchmark
Step 3: 对所有 Benchmark 样本计算 region_score
Step 4: 画出 CLEAR OUT / CANDIDATE / Hard Negative 的 score 分布
Step 5: 基于分布选择 T_low（确保 CLEAR OUT 中不包含可回答的问题）
Step 6: 在验证集上评估指标
Step 7: 调整阈值直到满足目标
```

### 12.4 阈值选择原则（按优先级排序）

| 优先级 | 原则 | 说明 |
| --- | --- | --- |
| **①** | False Accept Rate 最低 | 首要指标，尤其是 Hard Negative 子集 |
| **②** | Hard Negative False Accept Rate ≤ 目标值 | FA 中最危险的子类 |
| **③** | LLM Call Ratio 可控 | 受 CANDIDATE 比例影响，但不是硬性约束 |
| **④** | False Reject Rate 可接受 | 次要指标 |
| **⑤** | 延迟可接受 | 工程约束 |

**CANDIDATE 比例不作为硬性成功标准**。一个 CANDIDATE=80% 但 False Accept=0% 的系统，优于 CANDIDATE=20% 但 False Accept=12% 的系统。

### 12.5 区域差异化阈值

V0.2 先使用全局 `T_low`。在 Benchmark 校准后，如果发现不同知识区域的 region_score 分布差异显著，再考虑为每个区域设置独立阈值。

```
V0.2: 全局 T_low
V0.3+: 评估是否需要区域差异化阈值
```

### 13.3 Cache 失效策略

| 触发条件 | Exact Query Cache | Canonical Cache |
| --- | --- | --- |
| Boundary Version 升级 | 全部失效 | 全部失效 |
| Threshold Version 变更 | 全部失效 | 仅 CANDIDATE 条目失效 |
| Knowledge Coverage Matrix 更新 | 受影响区域条目失效 | 受影响区域条目失效 |
| Embedding Model 变更 | 全部失效 | 全部失效 |
| Deterministic Normalization 词典更新 | 不受影响 | 受影响条目失效 |

### 13.4 一致性保障机制总结

```
┌─────────────────────────────────────────────────────┐
│                  一致性保障层次                       │
│                                                     │
│  1. Exact Query Cache  → 完全相同文本 → 100% 一致    │
│  2. Deterministic Norm  → 规则/词典确定，无随机性     │
│  3. Canonical Cache     → 相同标准化结果 + 签名校验   │
│  4. answerability_signature → 防止不同可回答性合并    │
│  5. temperature=0       → LLM 判定可重复              │
│  6. 固定 Prompt         → 消除 Prompt 漂移             │
│  7. 版本化              → 变更可追溯                   │
└─────────────────────────────────────────────────────┘
```

### 13.5 三级一致性测试

**Level 1：Exact Consistency**

完全相同的文本 → 必须 100% 一致。

```
Q == Q → 结果必须相同
```

**Level 2：Semantic Paraphrase Consistency**

同义改写 → 目标 ≥ 95% 一致。

```
"为什么大家喜欢 AK？"
"AK 为什么这么受欢迎？"
"玩家为何偏好 AK？"
→ 结果应该相同
```

**Level 3：Boundary-Preserving Perturbation**

这是最重要的测试层级。不仅测试"相似问题是否一致"，还测试**"发生关键语义变化时，边界是否正确翻转"**。

```
"CS2 AK 使用率是多少？"     → IN
"CS2 里 AK 的使用比例是多少？" → IN  (应保持不变)

"CS2 AK 使用率是多少？"     → IN
"CS2 玩家为什么喜欢 AK？"    → OUT (应正确翻转)
```

Level 3 比单纯的 paraphrase consistency 更重要，因为它验证的是系统能否**区分"语义相似但 Answerability 不同"的问题**。

## 14. Boundary Calibration Benchmark

### 14.1 目的

为阈值选择和系统评估提供标准化测试集。

### 14.2 设计原则

> **不固定数量，按边界风险覆盖设计。** Benchmark 从 Knowledge Coverage Matrix 系统采样而来，而非人工随意编写。

### 14.3 构建流程

```
Step 1: 完成 Knowledge Coverage Matrix
         ↓
Step 2: 识别矩阵中的边界风险点
         ↓
Step 3: 按边界风险矩阵采样
         ↓
Step 4: 编写具体问题 + 变体
         ↓
Step 5: 人工审核 Expected 标签
```

### 14.4 边界风险覆盖矩阵（决定 Benchmark 结构）

Benchmark 应覆盖以下维度组合，确保各方向边界均匀：

| Domain | Topic | Question Type | Evidence Type | Evidence Level | Expected | 风险等级 | 重点扩展 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| IN | IN | IN | IN | IN | **IN** | 低 | 基础覆盖 |
| IN | IN | IN | IN | OUT | **OUT** | **极高** | **Hard Negative，重点扩展** |
| IN | IN | IN | OUT | — | **OUT** | **极高** | **Hard Negative，重点扩展** |
| IN | IN | OUT | IN | IN | **OUT** | 高 | 重点覆盖 |
| IN | IN | OUT | OUT | — | **OUT** | 中 | 基础覆盖 |
| IN | OUT | IN | IN | IN | **OUT** | 中 | 基础覆盖 |
| IN | OUT | IN | OUT | — | **OUT** | 低 | 基础覆盖 |
| IN | OUT | OUT | — | — | **OUT** | 低 | 基础覆盖 |
| OUT | — | — | — | — | **OUT** | 低 | 基础覆盖 |

**重点扩展方向**：

- **(IN, IN, IN, IN, OUT) → OUT**：Hard Negative，数据库有该类型数据但粒度不够。这是 V0.2 新增的最危险失败模式。
- **(IN, IN, IN, OUT, —) → OUT**：Hard Negative，语义接近但证据类型不匹配。系统需要拒绝"问法对但数据类型不对"的问题。
- **(IN, IN, OUT, IN, IN) → OUT**：数据库有数据但问题类型不支持。系统需要拒绝"问法不对"的问题。

### 14.8 评估指标（🔴 C5 统一）

**V0.2 统一指标命名**：

| 优先级 | 指标 | 英文 | 公式 | 说明 |
| --- | --- | --- | --- | --- |
| **①** | 假接受率 | False Accept Rate (FAR) | FA / (FA + TR) | **首要指标**。TR = True Reject |
| **②** | Hard Negative 假接受率 | Hard Negative FAR (HN-FAR) | FA_HN / (FA_HN + TR_HN) | Hard Negative 子集的 FAR，最关键的细分指标 |
| **③** | LLM 调用率 | LLM Call Ratio | LLM_Count / Total_Count | 仅非 CLEAR OUT 触发 LLM |
| **④** | 假拒绝率 | False Reject Rate (FRR) | FR / (FR + TA) | 次要指标。TA = True Accept |
| **⑤** | 精确率 | Precision | TA / (TA + FA) | IN 判定的准确率 |
| **⑥** | 召回率 | Recall | TA / (TA + FR) | IN 的召回率 |
| **⑦** | F1 | F1 | 2 × P × R / (P + R) | 综合参考 |

**术语统一规则**：

- **FAR = False Accept Rate**：在所有实际 OUT 的样本中，被错误判定为 IN 的比例
- **FRR = False Reject Rate**：在所有实际 IN 的样本中，被错误判定为 OUT 的比例
- **不再使用 FPR（False Positive Rate）**：该术语在分类问题中与 FAR 等价，但在边界检测上下文中 FAR 更直观
- **不再使用 FNR（False Negative Rate）**：统一使用 FRR

### 14.9 混淆矩阵

```
                    实际
                  IN    OUT
         ┌─────┬─────┬─────┐
    判  IN │ TA  │ FA  │     → Precision = TA / (TA + FA)
    定     ├─────┼─────┤
         OUT│ FR  │ TR  │     → FAR = FA / (FA + TR)
         └─────┴─────┘
              │     │
              ▼     ▼
        Recall =   FAR =
        TA/(TA+FR) FA/(FA+TR)
```

| 测试层级 | 变体类型 | 示例 | 期望 |
| --- | --- | --- | --- |
| Level 1 | 完全相同 | 原始问题重复 | 100% 一致 |
| Level 2 | 同义改写 | "玩家偏好 AK 的原因是什么？" | 结果一致 |
| Level 2 | 语序变化 | "AK 在 CS2 中为什么受玩家欢迎？" | 结果一致 |
| Level 2 | 缩写/口语 | "CS2 为啥玩家爱用 AK？" | 结果一致 |
| Level 3 | 关键语义变化（应翻转） | "CS2 AK 使用率是多少？" → "CS2 玩家为什么喜欢 AK？" | IN → OUT 正确翻转 |
| Level 3 | 关键语义变化（应翻转） | "AK 和 M4 哪个使用率高？" → "AK 下赛季会不会削弱？" | IN → OUT 正确翻转 |

## 18. 核心假设与验证计划

### 18.1 三大核心假设

#### H1：IN 与 OUT 的 score distribution 存在可利用的区分度

**假设**：在现有 Embedding 空间中，CLEAR OUT 和 CANDIDATE 的 region_score 上有显著差异，可以为 T_low 选择提供依据。

> **注意**：不预设具体的相似度数值范围（如 [0.75, 0.95]）。Cosine similarity 的绝对值高度依赖 embedding model、文本格式、中英文、query 长度、prototype 构造方法和数据分布。阈值由 Benchmark 决定，不能从论文中直接迁移。

**验证方法**：
1. 对 Benchmark 所有样本计算 region_score
2. 画出 CLEAR OUT / CANDIDATE / Hard Negative 三组的 score 分布
3. 检查 CLEAR OUT 和 CANDIDATE 的分布分离程度

**成功标准**：
- CLEAR OUT 和 CANDIDATE 的分布存在可见分离
- 可以找到 T_low 使得 CLEAR OUT 区域不包含任何实际 IN 的样本

**如果失败**（分布严重重叠）：
- 升级 Embedding Model
- 增加 Representative Vectors 数量
- 考虑引入 Mahalanobis distance（V0.3+）
- 考虑 Fine-tuned Embedding（V0.3+）

#### H2：False Accept Rate 可控制在目标范围内

**假设**：通过 CLEAR OUT 直接拒答 + Knowledge Coverage Matrix 类型级过滤 + LLM Evidence Judge 实例级验证的三层防护，可以将 False Accept Rate（尤其是 Hard Negative 子集）控制在可接受水平。

**验证方法**：
1. 在 Benchmark 上模拟不同 T_low 组合
2. 计算 FAR（全局 + Hard Negative 子集）
3. 计算 LLM Call Ratio（用于成本估计）
4. 计算 FRR（确保在可接受范围）

**成功标准**：
- FAR（全局）≤ 目标值
- HN-FAR ≤ 目标值
- FRR 在可接受范围
- LLM Call Ratio 不构成成本问题

> **注意**：CANDIDATE 比例不作为硬性成功标准。优先保证 FAR，而非追求低 CANDIDATE 比例。

**如果失败**（FAR 过高）：
- 调整 T_low 更保守（宁可更多进入 CANDIDATE）
- 完善 Knowledge Coverage Matrix（减少 MATRIX TBD 比例）
- 优化 LLM Judge Prompt 和 Knowledge Coverage Matrix
- 考虑增加 Hard Negative Vectors 在判定中的权重

#### H3：相似问题结果一致，关键语义变化时边界正确翻转

**假设**：Deterministic Normalization + 双层 Cache（含 answerability_signature）能保证 Level 1-2 一致性；LLM Judge（temperature=0）能保证 Level 3 的正确翻转。

**验证方法**：
1. 对 Benchmark 中每个问题的所有变体运行 Boundary Engine
2. Level 1: 检查完全相同文本的一致性
3. Level 2: 检查同义改写的一致性
4. Level 3: 检查 Boundary-Flip 变体是否正确翻转

**成功标准**：
```
Level 1 (Exact):            一致性 = 100%
Level 2 (Paraphrase):       一致性 ≥ 95%
Level 3 (Boundary Flip):    正确翻转率 ≥ 95%
```

**如果失败**（一致性不足）：
- Level 1 失败 → Exact Cache 实现有 bug
- Level 2 失败 → Deterministic Normalization 词典/规则不够完善，或 answerability_signature 过于敏感
- Level 3 失败 → LLM Judge 对关键语义变化不够敏感，需优化 Prompt 或 Knowledge Coverage Matrix

### 18.2 验证时间线

```
Week 1-2: Knowledge Coverage Matrix 构建
Week 2-3: Benchmark 构建（从 Matrix 系统采样）
Week 3-4: H1 验证（Score 分布分析）
Week 4-5: H2 验证（FAR 评估）
Week 5-6: H3 验证（一致性 + 翻转测试）
Week 6:   综合评估报告
```

### 18.3 V0.2 新增假设

#### H4：answerability_signature 能有效防止不同可回答性问题的错误合并

**假设**：通过 entity_type、question_subtype、修饰词检测等字段，answerability_signature 能区分"标准化结果相同但可回答性不同"的问题。

**验证方法**：
1. 在 Benchmark 中标记所有"Canonical 相同但 Answerability 不同"的问题对
2. 验证每对问题的 answerability_signature 是否不同
3. 如果存在签名相同但可回答性不同的问题对，分析遗漏的区分维度

**成功标准**：
- 所有 Benchmark 中 Canonical 相同但 Answerability 不同的问题对，answerability_signature 不同
- 签名相同且 Answerability 相同的问题对，签名一致性 = 100%

**如果失败**（签名区分度不足）：
- 增加更多区分字段（如 entity_count、question_complexity）
- 考虑引入轻量级语义 hash（非 LLM，如对关键短语做 embedding hash）

## 附录 A：术语表

| 术语 | 英文 | 定义 |
| --- | --- | --- |
| 可回答性 | Answerability | 数据库是否拥有足够证据以支持该问题类型的可靠回答 |
| 证据支持的可回答性 | Evidence-Backed Answerability | 强调 Answerability 必须由证据支撑，不能仅由语义相似度推导 |
| 边界检测 | Boundary Detection | 判断用户问题是否在系统知识边界内的过程 |
| 知识覆盖矩阵 | Knowledge Coverage Matrix | Region × Intent × Question Type × Evidence Type × Evidence Level → Answerability 的映射表 |
| 候选覆盖检测 | Candidate Coverage Detection | 通过 Embedding 判断问题"像不像数据库知识"（不是边界检测，产出 CANDIDATE / CLEAR OUT） |
| 知识覆盖检查 | Knowledge Coverage Check | 基于 Matrix 做类型级确定性过滤（产出 MATRIX IN / MATRIX OUT / MATRIX TBD） |
| 证据判定 | Evidence Judge | LLM 判断数据库是否真的能回答该问题（实例级验证，产出最终 IN/OUT） |
| 候选区 | CANDIDATE Zone | region_score ≥ T_low，问题语义接近数据库知识，需要下游验证 |
| 明确出界 | CLEAR OUT | region_score < T_low，问题语义明确远离数据库知识，直接拒答 |
| 硬负例 | Hard Negative | 语义接近数据库内容但实际超出数据库能力的问题 |
| 假接受 | False Accept (FA) | 实际 OUT 但被判定为 IN |
| 假接受率 | False Accept Rate (FAR) | FA / (FA + TR)，首要评估指标 |
| 假拒绝 | False Reject (FR) | 实际 IN 但被判定为 OUT |
| 假拒绝率 | False Reject Rate (FRR) | FR / (FR + TA)，次要评估指标 |
| 确定性标准化 | Deterministic Normalization | 用规则/词典/实体映射做标准化，不用 LLM |
| 可回答性签名 | Answerability Signature | 用于区分"标准化结果相同但可回答性不同"的问题的签名 |
| 开放集识别 | Open-Set Recognition | 识别系统需要能够拒绝未知输入，而非强制归类 |
