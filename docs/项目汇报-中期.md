## 一、项目架构与基本设计

### 1.1 我们要解决什么问题

游戏用研团队日常工作中，需要反复和不同类型的玩家做深度访谈，了解他们对新玩法、新题材、新商业化设计的反应。但真实访谈成本高、周期长、样本有限。我们的目标是构建一个 **AI 模拟用户系统**，让用研经理和游戏策划能够像和真人深访一样，随时与虚拟玩家对话，快速验证假设。

### 1.2 两条产品线

**群体画像**（群体级）— 基于 70+ 篇真实玩家访谈笔录，通过冰山模型标注 → Embedding 向量化 → M1 半监督分类，形成 5 种典型玩家画像（C1-C5）。用研人员选择特征标签（诉求/能力/风格/平台/模式）即可匹配画像，进入虚拟访谈室对话。

**KOL 数字孪生**（个体级）— 基于两位 B 站硬核测评 UP 主（冷面叶星星IKGN、鬼王陆行）的全量公开视频内容，构建「像这个人本人一样思考和表达」的 AI 分身。用户可以与 KOL 分身 1v1 对话，获取专业视角的游戏评价反馈。

两者的核心区别：群体画像回答"这类玩家会怎么想"，KOL 分身回答"这个 UP 主会怎么说"。

### 1.3 技术架构

```
┌──────────────────────────────────────────────────────────┐
│                   前端 (React 18 + shadcn/ui)             │
│  画像系统 (/personas) · KOL分身 (/kol) · 虚拟访谈室 (SSE)    │
└──────────────────────┬───────────────────────────────────┘
                       │ HTTP / SSE
┌──────────────────────▼───────────────────────────────────┐
│                后端 (Bun + Hono + Drizzle)                │
│  API 路由 · System Prompt 组装 · RAG 检索 · SSE 流式        │
└──────┬──────────────────────┬────────────────────────────┘
       │                      │
  ┌────▼─────┐           ┌─────▼────────┐
  │PostgreSQL│          │ Python Embed │
  │+pgvector │          │  Server :8765│
  │          │          │ bge-large-zh │
  │personas  │          │  -v1.5       │
  │kol_*     │          │ 1024-dim     │
  │chat_*    │          └──────────────┘
  └──────────┘
```

**技术选型要点**：

- **TypeScript (Bun)** 作为主体语言 — 前后端统一类型，共享 Zod Schema
- **Python** 仅用于 embedding 推理 — bge 模型在 Python 生态最成熟，通过 FastAPI 微服务暴露接口
- **DeepSeek** 作为 LLM — 中文能力强，API 兼容 OpenAI，价格低
- **pgvector** 作为向量数据库 — 复用现有 PostgreSQL，零额外运维

**技术选型中的探索与弯路**：

这个架构不是一开始就确定的。核心矛盾在于：项目主体是 TypeScript（Bun 运行时），但 embedding 模型 bge-large-zh-v1.5 和聚类算法 HDBSCAN、UMAP 全部是 Python 生态的原生库，JS/TS 侧没有同等成熟度的对应物。我们先后试了四条路径才最终收敛：

1. **纯 TS — transformers.js**：理论上可以把 HuggingFace 模型转成 ONNX 格式在 Bun 里跑推理。实际执行时 `@xenova/transformers` 包安装即卡死——ONNX 运行时二进制 ~300MB，Bun 的依赖解析在下载原生模块时反复超时。放弃。
2. **纯 JS — TF-IDF**：作为零依赖替代方案，用词频-逆文档频率做向量化。能跑通全量 389 条，但效果是关键词匹配而非语义匹配——搜"撤离射击"能召回含"撤离点"的片段，但搜"塔科夫"召回不了讨论塔科夫但不提这三个字的片段。作为临时验证够用，作为最终方案精度不够。
3. **Python — HuggingFace 直连**：改用 Python 的 sentence-transformers 直接加载 bge 模型。首次运行需从 huggingface.co 下载 1.2GB 权重文件，连接超时。
4. **Python — ModelScope 镜像**：通过国内可用的 ModelScope 镜像下载模型到本地缓存，sentence-transformers 从本地路径加载。这条路径最终跑通。

教训：不要为了"架构统一"牺牲工具成熟度——HDBSCAN 在 JS 生态没有靠谱实现，用 k-means 代替等于换了算法，方法论层面就变了。跨语言不是禁忌，关键是把边界划清楚：Python 只做模型推理这一件事，TS 继续管 Web 框架和业务逻辑。国内开发环境下，模型和依赖下载要多备几条镜像路线。

### 1.4 数据管线

```
原始数据 → 清洗/切片 → LLM 打标 → Embedding → 聚类 → 画像
                                                  │
                                            ┌─────┘
                                            ▼
                                    虚拟访谈室 (RAG + SSE)
```

核心链路已经验证通过。数据从真实访谈笔录/B 站视频出发，经过结构化处理后入库，再通过 LLM 提取特征、生成 embedding，最终在对话系统中通过向量检索 + System Prompt 约束实现角色一致的 AI 回复。

### 1.5 核心技术实现



#### 数据库设计

系统围绕四条核心表构建：

**群体画像侧**：`source_segments`（15,395 条有效访谈片段，含原始文本、说话人角色、冰山模型标注 JSON、1024 维向量）、`personas`（画像定义，含标签组合、M1-M5 动机因果链、关联证据 ID）、`chat_sessions`（对话记录，含会话级消息 JSON）。

**KOL 分身侧**：`kol_profiles`（UP 主画像，含 LLM 提取的 personaCard 和 styleProfile JSONB）、`kol_segments`（2,871 条语料片段，含视频来源 BV 号、1024 维向量、广告分类标签）。

所有表通过 Drizzle ORM 管理，Migration 文件版本控制。pgvector 扩展提供 HNSW 索引，向量相似搜索查询延迟 <10ms。

#### 画像提取

**群体画像**：采用冰山模型五层框架（M1 动机 → M2 期待 → M3 认知 → M4 感受 → M5 行为），结合枪战用户分析框架四维度（诉求/资产/能力/甜区）。AI 打标 v3.0 完成全量标注（冰山五层 + 框架四维 + 有效性判断），基于 M1_motivation 半监督分类产出 5 个聚类画像（C1-C5，718 名受访者分配，15% 阈值支持多标签），与画像假设 v1.2 的「5 主画像」重构结论对齐。

**KOL 画像**：将每位 UP 主清洗后的全量语料（5-13 万字）送入 DeepSeek Chat，JSON mode 强制结构化输出。提取两份画像——`personaCard`（身份定位、内容领域、评价体系维度权重）和 `styleProfile`（语气倾向、平均句长、说话风格描述）。关键设计：Prompt 中显式约束排除"大家好我是""投币点赞收藏"等 B 站通用套话，仅保留该个体独有的风格信号。LLM 调用失败时自动降级为统计方法（褒贬词频 + 句长分析）。

#### RAG 检索增强生成

KOL 对话的 RAG 链路是三段式：用户问题 → Python Embed Server（FastAPI :8765，bge-large-zh-v1.5 实时向量化）→ pgvector `<=>` 余弦距离排序 → Top-3 召回。召回结果自动过滤 `ad_label = '广告口播'` 的片段（通过 17 个广告品牌/术语关键词预标注）。Embed 服务不可用或 pgvector 查询失败时，自动 fallback 到 ILIKE 模糊匹配。

群体画像侧 10,897 条片段已完成 embedding 灌入（bge-m3，HNSW 索引），对话侧向量检索升级进行中，当前仍走 ILIKE 模糊匹配。

#### 广告检测

KOL 视频中夹杂大量外设推广（手柄、笔记本、云电脑），直接入库会污染 RAG 检索质量。解决方案：关键词快筛（17 个广告术语）→ ≥3 命中判为"广告口播"（RAG 排除），1-2 命中判为"混合"（保留），0 命中判为"测评内容"。389 条中检出 6 条广告，手工抽检确认无漏判。

#### 对话引擎

System Prompt 由画像字段动态组装，包含五个模块：身份声明（"你是 XXX，B 站硬核测评 UP 主"）、内容领域、评价体系约束（手感/玩法/画面/叙事的维度权重）、说话风格、RAG 检索到的往期相关内容作为证据上下文。五条硬性规则约束角色一致性：第一人称口语化、符合评价体系不自相矛盾、不懂就说不知道、禁止 AI 话术、有个性有态度。

输出采用 SSE 流式协议，Hono `streamSSE()` 推送，事件序列为 `data: {token}`（逐字）→ `data: {"type":"evidence","ids":[...]}`（溯源）。

#### 关键选型决策一览


| #   | 决策项          | 选择                        | 排除的方案              | 排除原因                                  |
| --- | ------------ | ------------------------- | ------------------ | ------------------------------------- |
| 1   | 语言运行时        | TS(Bun) + Python 局部       | 纯 TS               | transformers.js 安装不稳定，HDBSCAN 无 JS 实现 |
| 2   | LLM          | DeepSeek Chat             | GLM / MiniMax      | GLM key 失效；MiniMax 价格高且不需要多模态         |
| 3   | Embedding 模型 | bge-large-zh-v1.5 (1024维) | bge-small / TF-IDF | small 维度不匹配；TF-IDF 无语义，精度不够           |
| 4   | 向量数据库        | pgvector                  | Milvus / Chroma    | 389 条数据不需独立向量库；复用 PG 零运维              |
| 5   | 画像提取         | LLM 直接提取                  | HDBSCAN 聚类         | KOL 仅 2 人，无法聚类；群体画像待打标后用              |
| 6   | RAG 检索       | pgvector 向量搜索 + ILIKE 兜底  | 纯 ILIKE            | 关键词匹配漏召回严重                            |
| 7   | 广告检测         | 关键词快筛                     | LLM 逐条分类           | 389 次 API 调用成本高；实测关键词准确度足够            |
| 8   | 部署           | GHCR + CVM Docker         | 腾讯云 TCR / 服务器直建    | TCR 需额外凭据；直建无法回滚                      |

### 3.3 部署与运维

**部署架构**：腾讯云 CVM（Ubuntu）上运行 3 个 Docker 容器——mu-postgres（pgvector 数据库）、mu-api（Bun + Hono 后端）、mu-web（nginx 前端）。通过 GitHub Actions CI/CD 自动构建并推送 Docker 镜像到 GHCR，CVM 上 self-hosted runner 拉取部署。

**部署流程**（`deploy/docker-compose.prod.yml`）：

```
本地 push → GitHub Actions build job
  ├── apps/api/Dockerfile → ghcr.io/julia-lars/muru-thinktank-api
  └── apps/web/Dockerfile → ghcr.io/julia-lars/muru-thinktank-web
       ↓
deploy job (CVM self-hosted runner)
  ├── 1. 拉取最新镜像
  ├── 2. 启动 postgres (pgvector/pgvector:pg16)
  ├── 3. 等待 healthy → 运行 migration (drizzle)
  ├── 4. 执行 seed (personas + KOL)
  └── 5. 启动 api (Bun :3000) + web (nginx :80)
```

**关键技术点**：

- **多阶段构建**：Docker 分为 deps → prod-deps → builder → runner 四阶段，typecheck 在 builder 中作为"质量门"（类型错 = 镜像构建失败）
- **数据持久化**：pgdata volume 独立挂载，重建容器不丢数据
- **环境变量管理**：`.env.prod` 存储敏感信息（DB 密码、API Key），通过 `--env-file` 注入容器，不提交 Git
- **健康检查**：postgres（pg_isready）→ api（wget /api/health）→ web（nginx），依赖链保证启动顺序
- **回滚策略**：每个镜像带 SHA 标签（如 `sha-ab1234`），出问题可直接切回旧版本

**实际部署迭代**：

- 初期 CI/CD 正常，之后 CVM 上 self-hosted runner 意外停止，导致代码推送后自动部署中断
- 过渡期做法：直接 SSH 到 CVM 手动执行 `git pull → docker build → docker compose up`
- GitHub 连接不稳时的兜底：rsync 全量同步代码到 CVM 后再构建
- 当前公网地址：**[http://49.232.59.125](http://49.232.59.125)**，三个容器健康运行
